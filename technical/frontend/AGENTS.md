# Инструкции для агента: фронтенд

Применяй [общие правила](../../AGENTS.md). Начинай с F-документа своей стороны, затем читай связанную бизнесовую фичу и применимые стандарты. Подтверждённые стек и область его применения находятся в [обзоре фронтенда](README.md); не переноси их на другой клиент автоматически.

## Форма описания

Используй [шаблон frontend-фичи](../../templates/frontend-feature.md). Нужны страницы, значимые экраны, карта FSD-блоков, их ответственность и логическая компоновка. Раскрывай `features`, `widgets`, `entities`, `shared` и `pages` только в необходимом для сценария объёме. F-документ не равен одному срезу слоя `features`, а экран не вводит отдельный слой FSD.

Для нового или изменяемого блока укажи назначение, входы, выходы, владельца состояния, зависимости и места использования. Общий блок описывается один раз; при повторном использовании поставь ссылку и опиши локальную настройку. Не создавай дополнительные слои, компоненты и глобальные stores ради заполнения таблиц.

## Компоновка без вёрстки

Для каждой страницы/экрана покажи состав текстовым деревом и опиши связи: кто передаёт выбранный объект, кто выполняет действие, кто принимает результат и какие представления обновляются. Различай UI-вложенность и зависимости кода. Карта должна объяснять совместную работу, а не только перечислять имена.

Не включай реализацию Razor/HTML, CSS, сетки, размеров, отступов, breakpoints и pixel-perfect макетов. Названия компонентов и логические интерфейсы допустимы. Отсутствие вёрстки не отменяет описания поведения, ошибок, состояния и функциональной доступности.

## Данные, API и границы

Описывай пользовательское взаимодействие, источник данных, владение локальным состоянием и использование серверных операций. Связывай действия с backend F/DF или актуальным OpenAPI, не создавай вторую копию DTO. Для веб-UI используй согласованный NSwag-клиент; точные имена и конфигурацию не восстанавливай по догадке. Generated-код не редактируй вручную.

Клиентские `entities` не являются серверными агрегатами или EF-моделью. Не добавляй зависимость браузерного UI на Domain/EF ради повторного использования моделей. Проверка формы и блокировка кнопки не являются серверной авторизацией.

Не назначай без решения routes, состав форм, autosave, offline, cache, способ входа и тестовые библиотеки. Незакрытое оформляй в `questions/` и связывай с фичей; известную часть описывай конкретно. Подробная совместимость клиентов остаётся отложенной.

## Проверки и размещение

Проверки связывай с действиями и наблюдаемым результатом: основной путь, применимые ошибки, сохранение контекста, повтор, отмена и координация блоков. Применяй [S05](standards/S05-ui-and-forms.md), [S06](standards/S06-api-client.md), [S07](standards/S07-accessibility.md) и [S08](standards/S08-testing.md). Не превращай поведенческую проверку в требование описывать CSS или писать весь тестовый исходник в документации.

Модуль содержит карту и межфункциональные связи; детали отдельных блоков остаются в F-документах. Стандарты независимы от проекта, включая примеры и ссылки. Открывай только относящиеся к задаче документы.

После изменения проверь относительные ссылки, совпадение F-ID, соответствие состава страниц карте блоков, владельцев состояния и связь действий с результатами/проверками. Проверку текста не называй тестом работающего приложения.
