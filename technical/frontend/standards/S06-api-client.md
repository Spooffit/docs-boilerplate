# S06. Работа с API

## Область применения

Клиентские приложения, использующие внешние операции сервера.

## Форматы и границы

DTO и операции соответствуют фактическому публичному формату. Возможность сериализовать внутренний объект не делает его внешним API. Ручная копия серверной модели не должна становиться независимым определением взаимодействия.

Клиент обращается к предусмотренному внешнему интерфейсу, а не к внутренним механизмам приложения. Идентификаторы разных объектов и состояний не подменяются друг другом.

## Доверие и доступ

Клиентские сведения не являются доказательством права. Параметры серверного решения о доступе не выбираются самим получателем данных. Секреты не помещаются в журнал или случайный URL.

Совпадение контрольной суммы или локальное кэширование может уменьшить обмен, но не отменяет проверку доступа на сервере.

## Ошибки и повторы

Клиент различает ошибку ввода, отказ доступа, конфликт состояния и неизвестный сетевой исход. Отказ не отображается как успешное выполнение.

Повтор изменяющего запроса допускается только в пределах гарантий взаимодействия. Сроки сессий и правила обновления токенов задаются спецификацией приложения, а не предполагаются по поведению формы.

## NSwag как клиентская модель

Для web UI, использующего NSwag-клиент, generated classes являются основными клиентскими моделями API и используются напрямую в read/edit UI state.

Не создавать параллельные DTO/ViewModel/FormModel/EditorModel с теми же бизнесовыми полями ради формы. Generated code не редактируется вручную.

Отдельно от NSwag model допустимо хранить только presentation-state, которого нет в API-контракте: loading/dirty flags, выбранный UI node, раскрытые секции, pending operation, отображение validation и другие чисто интерфейсные сведения.

Если существующий OpenAPI/DTO неудобен или недостаточен для корректного UI use case, изменяется server contract и перегенерируется NSwag client. Постоянная ручная копия модели для обхода контракта не вводится.

Маппинг между двумя одинаковыми клиентскими представлениями без реальной семантической причины запрещён как лишняя точка расхождения.
## ETag / If-Match

Технический optimistic-concurrency token не хранится в NSwag DTO.

Для exact mutable resource API возвращает HTTP `ETag`. Frontend хранит ETag как техническое API/UI-state **рядом** с NSwag model.

Допустимая форма client-state:

```text
Data: <NSwag-generated DTO>
ETag: string
```

Это не отдельная business/ViewModel: DTO остаётся generated-моделью, а ETag — transport metadata.

State-changing request существующего mutable resource отправляет сохранённый ETag в:

```http
If-Match: "<etag>"
```

После successful mutation frontend сохраняет новый ETag из ответа либо перечитывает exact resource.

Если используемый NSwag client по умолчанию не предоставляет response headers, изменяется конфигурация генерации/общая API-client infrastructure так, чтобы ETag был доступен. Не создавать копию DTO только ради заголовка.

Поведение ошибок:
- `412 Precondition Failed` — representation изменился; не повторять mutation вслепую, сохранить локальный ввод где возможно и предложить перечитать актуальное состояние;
- `428 Precondition Required` — ошибка client flow/контракта: mutation была отправлена без обязательного ETag;
- `409 Conflict` — предметный конфликт (например stale-base), а не optimistic concurrency.

List responses не дают concurrency ETag каждой строки. Перед mutation из list UI должен получить exact resource/его ETag либо перейти через flow, который его уже загрузил.

Frontend не читает и не вычисляет внутренний `int Version` сервера.
