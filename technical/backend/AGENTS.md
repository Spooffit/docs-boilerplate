# Инструкции для агента: бэкенд

Применяй [общие правила](../../AGENTS.md). Начинай с F-документа своей стороны, затем читай связанную бизнесовую фичу и применимые стандарты.

## Форма серверной фичи

Используй [шаблон](../../templates/backend-feature.md). Нужна подробная спецификация реализации: Domain и владение состоянием; Application.Abstractions и модели; команды/запросы; транспортные и внутренние потоки; Application, Persistence, Integration и Host; DI; транзакции, конкуренция и ошибки; события; диагностика; стратегия тестирования.

Внешняя таблица следует [S17](standards/S17-data-flows.md), HTTP-часть [S16](standards/S16-rest.md). Для каждого DF-потока раскрывай конкретные чтения, преобразования, проверки, записи, момент фиксации и результат. HTTP-раздел не повторяет алгоритм handler, но алгоритм обязательно остаётся во внутренней обработке этой фичи.

Модели определяй один раз. Различай request DTO, application model, доменный parameter object и хранимое состояние. Не выдавай проектное имя нового класса за уже существующий исходник. Не придумывай маршруты, permissions, лимиты и коды ошибок по аналогии с другой фичей; оставляй `Уточняется` и ссылку на Q-документ.

## Валидация, выборки и размещение обработчиков

Применяй [S18](standards/S18-fluent-validation.md): FluentValidation, атомарные правила смысловых полей и композиция валидаторов. В фиче называй её конкретные переиспользуемые компоненты; не заполняй неизвестные ограничения догадками.

Для фильтрации применяй [S19](standards/S19-specifications.md): Ardalis.Specification и атомарные переиспользуемые условия. Не дублируй фильтры в обработчиках и не выдумывай API объединения готовых спецификаций.

По [S20](standards/S20-cqrs.md) command handler всегда располагается в Application; query handler в слое доступа к данным, обычно EntityFramework.Persistence.

## Проверки

Стратегия тестирования содержит SUT, собственные данные, реальные зависимости и допустимые doubles, изоляцию/cleanup и матрицу проверок по потокам. Применяй [S04](standards/S04-testing.md) и стандарты соответствующих категорий. Несколько BC внутри одного API не превращают Functional в E2E; для E2E нужен реальный необходимый контур приложений.

Форматы API связывай с актуальным исходником или формальной спецификацией. Наличие доменного метода не доказывает готовность внешней операции. Обещание выполнить `dotnet test` не является подтверждением прошедшего теста.

## Размещение и границы

Модуль содержит карту и межфункциональные связи; реализация отдельных действий остаётся в фичах. Открывай только относящиеся к задаче документы. Неопределённое оформляй в `questions/` и связывай с модулем/фичей через каталог.

Стандарты не содержат специфику проекта, даже в примерах и ссылках. Конкретные проверки, решения и применение стандарта описываются со стороны фичи, модуля или ADR. Подробная совместимость клиентов остаётся отложенной до отдельного обсуждения; изменение формы документа не расширяет её объём.

После изменения проверяй относительные ссылки, совпадение F-ID, согласованность DF/моделей/ошибок/тестов и отсутствие независимой копии бизнесового правила. Проверку текста не называй тестом работающего приложения.

## Нормативность feature-документов

Feature-документ (`business/features`, `technical/backend/features`, `technical/frontend/features`) описывает **последнее согласованное состояние** фичи.

Запрещено накапливать внутри feature хронологические секции вида `Решение блока N`, `Уточнение блока N`, старые отменённые варианты и последовательность обсуждений. Новое решение переписывает соответствующий нормативный раздел.

История выбора, альтернативы и происхождение решения остаются в `questions/` либо ADR. Feature может дать ссылку на связанный Q/ADR, но не копирует журнал переговоров.

Backend feature описывает реализацию по физическим слоям проекта: `Domain`, `Application.Abstractions`, `Application`, `Api`, `EntityFramework`, `EntityFramework.Persistence` и используемые external adapters (`S3`, `RabbitMQ/MassTransit`, `HTTP` и т.д.). Для каждого слоя указываются конкретные типы, поля, методы, ports, mappings и ответственность; общая фраза «реализовать по Clean Architecture» спецификацией не считается.
