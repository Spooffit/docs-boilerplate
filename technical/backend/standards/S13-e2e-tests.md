# S13. E2E tests

## Область применения

Проверка законченного бизнес-сценария через все deployable units, необходимые этому сценарию. SUT: соответствующий distributed application flow, а не один внутренний компонент.

Главный вопрос: **работает ли сценарий целиком так, как его видит внешний потребитель системы?**

## Граница сценария

Поднимается весь необходимый контур сценария, а не обязательно все сервисы solution.

```text
External request → Service A → RabbitMQ → Worker B → PostgreSQL
                                                      ↓
                                          Observable business result
```

Отсутствующие в сценарии сервисы не добавляются ради формального «полного окружения».

## Способ проверки

E2E максимально black-box. Проверяются исходное воздействие и конечный наблюдаемый результат. Не следует проверять, какой handler, repository, internal event handler или внутренний метод был вызван и сколько раз.

E2E не подменяется последовательностью вызовов внутренних методов с test doubles вместо реального необходимого межсервисного пути.

## Оркестрация для Aspire-приложений

Для .NET distributed application с подходящим AppHost используется Aspire testing infrastructure: `Aspire.Hosting.Testing` и `DistributedApplicationTestingBuilder`.

Окружение запускается через существующую модель application graph: API, workers, БД, брокер и другие требуемые ресурсы. Не следует вручную дублировать через Testcontainers всю topology AppHost без веской причины.

Если существующий AppHost не соответствует необходимому контуру, конкретная адаптация определяется при проектировании тестового окружения. Общий стандарт не задаёт имена ресурсов или сервисов конкретного приложения.

## Изоляция и ожидание

E2E имеет собственный lifecycle и не использует подготовку Functional или Integration. Параллельные окружения и их данные изолируются. Предел параллелизма тяжёлых E2E-сценариев настраивается отдельно.

Асинхронный поток ожидается по observable condition с timeout, polling interval, понятной диагностикой и cancellation.

## Проверка соблюдения

Запущен реальный необходимый граф приложений; тест проходит отдельно и совместно с остальными; результат проверен внешним наблюдением; окружение не оставляет созданные только для него ресурсы после завершения.
