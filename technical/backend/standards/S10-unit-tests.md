# S10. Unit tests

## Область применения

Изолированная проверка отдельного класса, небольшого компонента или локальной бизнесовой и прикладной логики.

## SUT

Подходящие объекты проверки: Domain logic, Application logic, value objects, domain services, policies, validators. Handler проверяется как Unit, если его зависимости разумно заменить test doubles.

Размер метода или название test project не определяют уровень теста. Если требуется доказать работу SQL, реального хранения или транспорта, это уже граница Integration, а не повод расширять Unit-окружение.

## Зависимости

Unit tests не поднимают Docker и не используют настоящие PostgreSQL, RabbitMQ или другие внешние технические ресурсы. Mocks, fakes и stubs допустимы, когда помогают изолировать SUT.

Нельзя объявлять проверенной инфраструктурную интеграцию только потому, что тест прошёл с её заменой.

## Независимость и скорость

Тесты создают необходимые данные и не используют результат другого теста. Они должны быть быстрыми, независимыми и хорошо параллелиться.

Ограничения, введённые для тяжёлых окружений Integration / Functional / E2E, не должны искусственно ограничивать Unit tests.

## Именование

Название каждого теста обязательно соответствует принятой рекомендации Microsoft: `MethodUnderTest_Scenario_ExpectedBehavior`. Состав частей и примеры определены в [общем правиле именования](S04-testing.md#именование-тестов).

## Проверка соблюдения

SUT явно ограничен. Для запуска не нужны Docker, внешняя БД или брокер. Тест проходит самостоятельно; замены зависимостей служат изоляции, а не скрывают проверяемую обязанность.
