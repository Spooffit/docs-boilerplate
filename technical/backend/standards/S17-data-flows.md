# S17. Потоки данных и транспортные взаимодействия

## Область применения

Технические спецификации функций с внешними взаимодействиями, межкомпонентной передачей данных или изменением постоянного состояния. Стандарт определяет способ описания, а не набор операций конкретного продукта.

## Два уровня описания

**Транспортный поток** фиксирует внешний договор: инициатор, транспорт, адрес, доступ, вход, вызываемое действие и наблюдаемый результат. **Внутренний поток** объясняет реализацию этого действия: преобразования, чтения, проверки, изменения, commit и последующие эффекты.

Они находятся в отдельных разделах одной серверной фичи и связаны идентификатором потока. HTTP-таблица не должна содержать последовательность repository calls. Внутренний алгоритм не должен заново определять поля внешнего DTO.

## Транспортные потоки

Для функции с внешними взаимодействиями обязательна таблица следующего состава. Идентификатор, например `DF01`, включается в название потока; он локален документу.

| Колонка | Назначение |
| --- | --- |
| Поток | ID и название пользовательского или системного взаимодействия. |
| Транспорт | HTTP API, Message broker, Outbox, Background job, Email, Import, Export либо иной явно указанный механизм. |
| Метод / канал | HTTP method, тип сообщения, job или канал взаимодействия. |
| Endpoint / destination | URL, адрес получателя, event, queue или иная точка назначения. |
| Доступ | Permission, роль, anonymous access либо проверяемое системное условие. |
| Вход | Route/query/body/header contract или message payload. |
| Application action | Command/query или иной application use case. |
| Выход | DTO, response contract, event, файл либо явное отсутствие данных. |
| Успех | HTTP status или другой наблюдаемый признак успешного завершения. |
| Ошибки | Значимые ожидаемые отказы этого потока. |

`Outbox` обозначает этап надёжного сохранения и отправки, а не обязательно самостоятельный сетевой транспорт. Для него отдельно указываются последующий транспорт и получатель. Фоновое задание также требует явного описания триггера и завершения; слово `job` не определяет расписание.

Ни одного автоматически добавленного транспорта: доменное событие в памяти не доказывает отправку в broker, а внутренний вызов use case не превращается в отдельный HTTP endpoint.

## Нейтральный пример транспортного потока

| Поток | Транспорт | Метод / канал | Endpoint / destination | Доступ | Вход | Application action | Выход | Успех | Ошибки |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| DF01. Получить запись | HTTP API | GET | `/api/v1/records/{id:guid}` | Условие доступа определяется контрактом | Route `id: Guid` | `GetRecordQuery` | `ApiResponse<RecordDto>` | 200 с представлением | 404 при отсутствии маршрута/записи; остальные отказы только по контракту |

Маршрут, типы и код успеха в примере иллюстративные. Пример не выбирает endpoint или право конкретного приложения.

## Подробное описание внутреннего потока

Для каждого изменяющего или нетривиального читающего действия описывается последовательность:

| Шаг | Исполнитель | Вход / чтение | Преобразование и проверка | Запись / выход |
| --- | --- | --- | --- | --- |
| 1 | Transport adapter | Внешний запрос | Binding, доверенный контекст, передача cancellation | Application input |
| 2 | Application | Вход и необходимые факты | Проверка ссылок, получение текущего состояния | Данные для доменного действия |
| 3 | Domain / application policy | Подготовленные значения | Инварианты и вычисление результата | Новое состояние либо отказ |
| 4 | Persistence boundary | Согласованный набор изменений | Concurrency и commit | Подтверждённое сохранение |
| 5 | Transport / dispatcher | Сохранённый результат | Mapping либо отправка подтверждённого эффекта | Внешний ответ / сообщение |

Таблица показывает форму, а не обязательные пять шагов любого сценария. В заполненной фиче используются её реальные операции, типы и источники. Формулировки «проверить и сохранить» без конкретных данных недостаточны. Простое чтение не получает искусственный доменный transition или transaction scope.

## Обязательные свойства нетривиального потока

Указываются владелец состояния и источник истины; что считается недоверенным входом; на каких версиях данных производится вычисление; где заканчивается атомарная запись; какие действия происходят после commit; что именно клиент может наблюдать.

Для потока с несколькими хранилищами явно перечисляются независимые фиксации. Запись в БД и загрузка файла не объявляются одной атомарной операцией без соответствующего механизма. Описываются частичный сбой и сохранение или компенсация уже выполненных эффектов.

Для чтения описываются фильтры, порядок, пагинация и согласованность набора там, где они имеют значение. Наличие read model не делает её автоматически актуальной.

## Повторы, конкуренция и асинхронность

Для применимых потоков фиксируются ключ повторного действия, область дедупликации, момент подтверждения сообщения, порядок обработки, реакция на устаревший вход, конкурирующие изменения и неизвестный результат после обрыва ответа. Если правило не определено, ставится `Уточняется`, а не обещание exactly-once.

Проверяются различия: запись outbox; приём broker; получение consumer; commit consumer; доступность результата. Успех одного этапа не выдаётся за завершение всей цепочки.

Timeout клиента не доказывает rollback на сервере. Отмена до commit, ошибка commit и отмена после commit описываются отдельно.

## Связь с моделями и тестами

Модель данных определяется один раз и получает ссылку из потоков. По каждому обязательному результату должны находиться входной поток, внутренний алгоритм и проверяющий тест. Матрица проверки содержит ID потока, сценарий, SUT, исходные данные, наблюдаемый результат и уровень теста.

Architecture проверяет границы; Unit проверяет изолированное преобразование; Integration проверяет настоящие хранилища и транспорт; Functional проверяет внешний вход одного приложения; E2E проверяет необходимую межприложенческую цепочку. Классификация не определяется именем handler.

## Неизвестные и неприменимые части

`Уточняется` означает отсутствие решения; `Не применяется` означает осознанное отсутствие механизма. Не подставляйте URL, queue, permission, срок или тип DTO только ради заполненной таблицы. Обоснованные предложения реализации отделяются от подтверждённых контрактов.

В применяющем документе неизвестное связывается с конкретным вопросом. Сам стандарт не содержит ссылок на проектные вопросы или список использующих его фич.

## Проверка соблюдения

Внешние взаимодействия перечислены, каждый нетривиальный поток имеет внутреннее раскрытие, типы и источники не противоречат друг другу, точки commit и наблюдаемости различимы, ошибки после частичного выполнения разобраны, повторы не обещают недоказанную идемпотентность, тесты связаны с результатами. Диаграмма или цепочка стрелок может дополнять таблицы, но не заменять их.
