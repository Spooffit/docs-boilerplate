# S15. Test engineering: общая инфраструктура, данные и проверка изменений

## Область применения

Организация reusable testing boilerplate, ожидание асинхронного результата, подготовка данных и перенос существующих тестов на самодостаточную модель.

## Общий тестовый boilerplate

Переиспользуемый технический код хранится внутри solution в общих testing-проектах. Если используется организация BuildingBlocks, она является предпочтительным местом для такого кода.

В общий слой могут входить Testcontainers builders; PostgreSQL/RabbitMQ fixtures; provisioning database и vhost; идентификаторы ресурсов; test environment context; connection string builders; cleanup; базовые WebApplicationFactory; Aspire helpers; eventually consistent assertions; async polling; lifecycle abstractions; определения parallel limits и общие test primitives.

Это не требование создать все перечисленные абстракции заранее. Общий механизм выделяется по фактическому повторному использованию.

Бизнесовые data builders конкретного контекста и fixtures отдельных сценариев остаются рядом с их тестами. Общий testing-слой не превращается в хранилище доменной логики.

## Ожидание eventual consistency

Для asynchronous flows нельзя использовать произвольный `Task.Delay` как доказательство завершения работы.

Механизм ожидания наблюдаемого условия должен иметь timeout, polling interval, понятную ошибку по истечении срока и поддержку cancellation. Проверяется условие результата, а не факт истечения выбранного количества миллисекунд.

```text
Read observable state
Check expected condition
Continue polling within timeout unless cancelled
Report a meaningful timeout failure when the condition is not met
```

Общий механизм ожидания может находиться в testing BuildingBlocks. Functional и E2E используют его для observable conditions, а не для инспекции случайных внутренних вызовов.

## Тестовые данные

Каждый тест создаёт собственные исходные данные. Он не предполагает заранее существующую запись с фиксированным ID, известного пользователя, пустую таблицу или очередь, созданную другим тестом.

Для параллельной работы используются уникальные идентификаторы там, где иначе возникнет пересечение. Результат другого теста не является предусловием.

## Структура тестовых проектов

Разделение отражает реальные SUT и виды тестов. Возможная организация: `ArchitectureTests`, `UnitTests`, `IntegrationTests`, `FunctionalTests`, `E2ETests`. При нескольких контекстах допустимы дополнительные проекты по контекстам, если это помогает сохранить границы.

Эти имена не обязательны. Не создаются проекты исключительно ради соответствия схеме папок.

Имена тестовых проектов и названия отдельных тестов — разные соглашения. Для каждого теста обязателен формат `MethodUnderTest_Scenario_ExpectedBehavior` по [правилу именования](S04-testing.md#именование-тестов), независимо от проекта, категории и test framework. При добавлении или изменении теста проверяется соответствие его названия этому правилу.

## Аудит

До изменения существующей инфраструктуры изучаются test projects, текущие и исторические тесты, архитектурные проверки, AppHost, Testcontainers/Aspire boilerplate, test framework, skipped/ignored tests и требуемые environment variables.

Для каждого теста определяются: реальный SUT, вид теста, правильный уровень размещения и действительно необходимые зависимости. Нельзя доверять только названию проекта или namespace.

## Проектирование и миграция

Определяются структура проектов, общие testing-компоненты, lifecycle, PostgreSQL/RabbitMQ isolation, запуск одного приложения, E2E-граф, parallelism limits, cleanup и конфигурация.

Существующие тесты не удаляются только потому, что их трудно адаптировать. При необходимости они перемещаются в правильный test project, получают новую fixture и освобождаются от обязательного manually configured environment.

Для Unit реальные зависимости заменяются test doubles, когда это соответствует SUT. Для Integration удаляются замены, которые скрывают саму проверяемую интеграцию. Тест, смешивающий несколько уровней, при необходимости разделяется.

Исторические тесты не копируются механически; устаревшие предположения пересматриваются относительно принятой архитектуры. Необходимые изменения production business behavior, публичных взаимодействий, структуры контекстов, production topology или схемы production-БД не считаются автоматически разрешёнными задачей на тестовую инфраструктуру.

## Расширение покрытия

Приоритет: явно формализуемые архитектурные ограничения, критичные инфраструктурные границы и основные application flows. Искусственная погоня за высоким coverage percentage не является целью.

Изменение тестового harness не должно незаметно переделывать предшествующие архитектурные решения, не относящиеся к задаче.

## Проверка из чистого состояния

Для .NET выполняется полный `dotnet test`, а также проверяются самостоятельный и совместный запуск test projects.

| Область | Признак корректного результата |
| --- | --- |
| Подготовка | Необходимая инфраструктура создаётся автоматически, внешние БД/брокеры вручную не готовятся. |
| Полнота | Обязательные тесты не превращаются в Skipped из-за отсутствия ручной подготовки. |
| Именование | Каждый тест назван по обязательному формату: проверяемый метод/операция/правило, сценарий, ожидаемое поведение. |
| Независимость | Каждый проект запускается отдельно и вместе с другими, без зависимости от порядка. |
| Изоляция | Данные БД и RabbitMQ не протекают между тестами; параллельные scopes не конфликтуют. |
| Lifecycle | Cleanup работает после ошибок; созданные только для прогона ресурсы освобождаются. |
| Параллелизм | Настроенные ограничения реально соблюдаются; сбой одного environment не повреждает другой. |
| Граница SUT | Integration не поднимает лишнюю систему; Functional запускает один SUT; E2E использует реальный необходимый application graph. |
| Лёгкие тесты | Architecture и Unit не требуют Docker. |

В отчёте о конкретном прогоне различаются требования к тестам, выполненные проверки и фактические результаты. Настоящий стандарт не является отчётом о запуске какого-либо приложения.
