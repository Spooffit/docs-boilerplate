# S04. Общая модель тестирования

## Область применения

Автоматические тесты программных систем. Приведённое распределение инструментов относится к .NET, ASP.NET Core и распределённым приложениям с контейнерной инфраструктурой. Оно не предписывает этот стек любому проекту.

## Цель

Тесты самодостаточны: самостоятельно поднимают, конфигурируют, изолируют и освобождают необходимые тестовые зависимости. Локальный запуск и CI не требуют заранее подготовленного внешнего сервера БД, брокера сообщений или вручную заданной строки подключения к нему.

Для .NET штатный полный запуск выполняется через `dotnet test`. Самодостаточность тестового окружения не означает автоматическую установку SDK или среды запуска контейнеров.

Отсутствие вручную подготовленного ресурса не должно превращать обязательный тест в `Ignored` или `Skipped`. Проблема подготовки окружения не считается успешной проверкой.

## Термины и классификация

SUT (System Under Test) означает проверяемую систему или компонент. Категория определяется реальным SUT, целью и способом взаимодействия, а не именем проекта или namespace.

| Категория | SUT и цель | Основной способ проверки | Инфраструктура |
| --- | --- | --- | --- |
| Architecture | Структура кода, сборок и зависимостей | Формализованные архитектурные ограничения | Без Docker и внешних ресурсов |
| Unit | Отдельный класс, небольшой компонент или локальная логика | Изолированное поведение, при необходимости test doubles | Без Docker, настоящих БД и брокеров |
| Integration | Код и одна или несколько реальных технических зависимостей | Корректность реальной интеграции; white-box/gray-box допустимы | Прежде всего Testcontainers |
| Functional | Одна функция одного deployable application | Публичный HTTP/gRPC/иной внешний интерфейс; наблюдаемый результат | Для ASP.NET Core: WebApplicationFactory и Testcontainers |
| E2E | Законченный сценарий через необходимые deployable units | Максимально black-box: исходное воздействие и конечный результат | Для соответствующего .NET-графа: Aspire testing и AppHost |

Это последовательное соглашение терминологии для документации и тестового кода. Integration не означает автоматически любой тест через HTTP; Functional и E2E различаются границей SUT.

## Разделение инструментов

**Testcontainers** предоставляет реальные disposable infrastructure dependencies: БД, брокер, S3-compatible storage, Redis и аналогичные технические ресурсы. Основные области: Integration и Functional.

**WebApplicationFactory** запускает один ASP.NET Core SUT для Functional, если архитектура приложения позволяет такой запуск. Testcontainers предоставляет его зависимости. Эти инструменты дополняют друг друга.

**Aspire.Hosting.Testing / DistributedApplicationTestingBuilder** запускает необходимый distributed application graph для E2E через подходящую модель AppHost. Не следует дублировать её топологию вручную без веской причины.

Для проверки `Repository ↔ PostgreSQL` не поднимается всё распределённое приложение. Один инструмент не должен искусственно обслуживать все уровни тестирования.

## Независимость наборов

Architecture, Unit, Integration, Functional и E2E не зависят от порядка выполнения. Каждый test project запускается самостоятельно. При изоляции окружений проекты могут выполняться вместе и параллельно.

Последовательность CI `Architecture + Unit → Integration + Functional → E2E` допустима как организация прогонов, но не как передача подготовленного состояния между наборами тестов.

## Приоритеты

При выборе решения соблюдается порядок: корректная семантика теста; изоляция; воспроизводимость; отсутствие ручной подготовки внешнего окружения; соответствие реальным production-технологиям; скорость; простота test boilerplate.

Изоляция важнее скорости. При этом физически отдельный контейнер не нужен там, где достаточно более дешёвой логической изоляции.

## Именование тестов

Рекомендация Microsoft [Follow test naming standards](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) принята как обязательное соглашение: название каждого теста содержит проверяемый метод, сценарий и ожидаемое поведение.

```text
MethodUnderTest_Scenario_ExpectedBehavior
```

Названия пишутся на английском языке: три содержательных части в PascalCase разделяются символом `_`. Например, `Add_SingleNumber_ReturnsSameNumber` и `Parse_InvalidInput_ThrowsFormatException`. По названию должно быть понятно, что проверяется, при каких условиях и какой результат ожидается. Названия вроде `Test1`, `Works` или `Parse_InvalidInput` не соответствуют соглашению.

Microsoft формулирует эту рекомендацию для Unit tests. Настоящий стандарт распространяет обязательное соглашение на Architecture, Unit, Integration, Functional, E2E и клиентские тесты. Если SUT не является отдельным методом, первая часть обозначает проверяемую операцию или правило: `GetResource_UnknownIdentifier_ReturnsNotFound`, `AssemblyDependencies_ForbiddenReference_ReportsViolation`. Не требуется привязывать название к закрытому методу реализации.

Параметризованный тест сохраняет тот же формат; подписи отдельных наборов данных дополняют, а не заменяют содержательное название теста. Строковые названия в runners без тестовых методов также следуют этому формату. Соглашение не требует конкретной библиотеки тестирования.

## Проверка соблюдения

Тесты классифицированы по SUT; названия соответствуют обязательному формату `MethodUnderTest_Scenario_ExpectedBehavior`; каждый набор самодостаточен; обязательные проверки не скрыты пропусками из-за ручной подготовки; данные и ресурсы не протекают между тестами; полный и отдельные прогоны воспроизводимы. Процент покрытия не подменяет проверку архитектурных ограничений, инфраструктурных границ и основных функций.
