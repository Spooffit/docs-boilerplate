# S14. Тестовые окружения: изоляция, lifecycle и параллельность

## Область применения

Integration, Functional и E2E с реальными инфраструктурными зависимостями. Architecture и Unit не должны получать зависимость от Docker ради общего test boilerplate.

## Самодостаточность и границы suites

Тесты автоматически создают, конфигурируют и освобождают свои окружения. Обязательная connection string к заранее подготовленному внешнему серверу не используется как условие запуска.

У каждого вида тестов собственные lifecycle и infrastructure scope. Integration не использует database/vhost Functional; Functional не зависит от окружения E2E. Ни один test project не выполняет обязательный setup другого.

## Физическая и логическая изоляция

Цель: гарантированная изоляция при разумной стоимости запуска, а не максимальное число контейнеров.

Предпочтительная модель там, где она обеспечивает корректность:

```text
Shared heavyweight resource within a test run
    ├─ isolated logical resource for scope A
    ├─ isolated logical resource for scope B
    └─ isolated logical resource for scope C
```

Не применяется автоматическое правило «один test method = полный набор контейнеров». Container-per-test нужен, когда сценарий действительно требует физически независимого instance.

## PostgreSQL

Параллельные тесты не должны изменять одну общую mutable database.

Допустимые стратегии: отдельная database на test; отдельная database на parallel worker / fixture с гарантированным reset между последовательными тестами; отдельный PostgreSQL container, когда более лёгкая изоляция недостаточна.

Один общий контейнер с отдельными databases предпочтительнее нескольких контейнеров, если разделение гарантирует корректность. Каждый параллельный test scope или worker получает собственное пространство БД.

При использовании reset-механизма, например Respawn, параллельный reset общей базы запрещён. Reset между последовательными тестами не обеспечивает безопасность одновременной работы с той же базой.

## RabbitMQ

Параллельные тесты не должны случайно разделять queues, exchanges и bindings.

Для общего RabbitMQ instance предпочтителен отдельный virtual host на изолированный test scope / parallel worker. Внутри vhost допустимы реальные production-like имена exchanges и queues: изоляция обеспечивается отдельным namespace.

Если vhost недостаточно, используются уникальные имена ресурсов либо отдельный контейнер. Отдельный broker прежде всего нужен при изменении broker-wide state и проверке restart, node-level configuration, plugins, global policies или failure/recovery самого брокера.

## Reuse

Тяжёлые ресурсы разрешено переиспользовать в пределах одного test run. Несколько последовательных методов могут использовать безопасно сбрасываемую fixture.

Reuse не разрешает state leakage. При риске смешивания состояния выбирается более строгая изоляция. Пример: один PostgreSQL container и один RabbitMQ container в рамках suite, но отдельные database и vhost для каждого параллельного scope.

## Управление параллелизмом

Максимум одновременно выполняемых heavy tests / environments настраивается централизованно и отдельно для Integration, Functional и E2E.

Предпочтительны штатные ограничения test framework. При использовании TUnit это его global maximum parallel tests, ParallelLimiter и custom parallel limits, а не собственный scheduler без необходимости.

Значения лимитов выбираются по ресурсам среды и остаются конфигурируемыми. Например, 4 для Integration, 4 для Functional и 2 для E2E являются только иллюстрацией начальной настройки, а не обязательными числами.

Architecture и Unit не ограничиваются искусственно лимитами тяжёлых окружений. Раздельные лимиты suites не отменяют необходимость проверить суммарную нагрузку при совместном запуске.

## Lifecycle

Каждая infrastructure fixture обеспечивает последовательность:

```text
Create → Start → Wait until ready → Configure → Use → Cleanup → Dispose
```

Имена контейнеров и host ports не фиксируются без необходимости. Динамические имена и порты предоставляются средствами Docker / Testcontainers / Aspire там, где это возможно.

Cleanup выполняется также после failed test. Созданные исключительно данным прогоном containers, networks, databases, vhosts и temporary volumes освобождаются. Ресурсы другого прогона не должны затрагиваться очисткой.

## Конфигурация

Переменные окружения могут настраивать test harness, например степень параллелизма. Они не должны быть обязательным способом указать внешний уже подготовленный сервер БД или брокер.

Имена переменных, образы, версии и размеры конкретного окружения определяются в конфигурации его реализации вне общего стандарта.

## Проверка соблюдения

Проверяются самостоятельный и совместный запуск suites, параллельные изменения, отсутствие пересечения данных, реальное соблюдение лимитов и очистка после ошибок. Сбой одного environment не повреждает другой. Infrastructure tests не получают случайную зависимость от порядка выполнения.
