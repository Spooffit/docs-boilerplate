# S19. Фильтрация сущностей: Ardalis.Specification

## Область применения

Фильтрация сущностей при чтении и получении данных для серверных операций .NET-приложения. Для описания условий отбора обязательно использовать паттерн **Specification** и библиотеку **Ardalis.Specification**. Разрозненные копии одинаковых условий в обработчиках и репозиториях недопустимы.

Стандарт не задаёт сущности, доступные фильтры или ограничения конкретного приложения. Они описываются в его функциональной спецификации.

## Атомарность

Каждое повторно используемое условие выделяется в минимальный самостоятельный компонент: отбор по одному смысловому полю либо неделимому отношению полей. Итоговая спецификация операции собирает необходимые условия и определяет форму результата.

Общее правило должно использоваться повторно во всех подходящих выборках. Изменение правила производится в одном месте. Совпадение имён полей без совпадения смысла не является основанием для общей спецификации.

Компонент фильтра добавляет только заявленное условие. Он не должен скрыто применять пагинацию, менять порядок, проекцию, tracking или отключать ограничения доступа. Эти аспекты выделяются отдельно и подключаются явно.

Не создаётся один универсальный класс со всеми возможными фильтрами, флагами и необязательными режимами. Атомарность определяется смыслом условия, а не искусственным требованием создавать класс для каждого оператора сравнения.

## Композиция с учётом API библиотеки

**Ardalis.Specification не предоставляет общего механизма объединения готовых спецификаций через AND / OR / NOT.** Нельзя проектировать вызовы вроде `specA.And(specB)` как существующий API библиотеки. Причина: готовая спецификация может содержать не только предикат, но и порядок, пагинацию, загрузку связей и проекцию. См. [официальное объяснение](https://specification.ardalis.com/getting-started/faq.html#how-do-i-use-composite-specifications).

Основной способ переиспользования: небольшие расширения `ISpecificationBuilder<T>` с именованными условиями. Конкретная `Specification<T>` вызывает эти расширения и собирает выборку. Если атомарный отбор нужен самостоятельно, отдельная спецификация использует то же расширение, а не переписывает условие. См. [расширения спецификаций](https://specification.ardalis.com/extensions/extensions-for-specifications.html).

```text
Общее условие поля / отношения
    → переиспользуемое расширение builder
        → спецификация конкретной выборки
        → при необходимости отдельная спецификация простого отбора
```

Несколько последовательных условий `Where` сужают выборку совместно. Альтернатива OR должна быть выражена явным предикатом с правильной группировкой; последовательное добавление двух условий не обозначает OR. Предикаты должны оставаться выражениями, пригодными для выбранного провайдера данных.

Не нужно писать собственный универсальный движок композиции полных спецификаций ради переиспользования простых условий.

## Выполнение и форма результата

Спецификация описывает выборку и не выполняет её: не открывает соединения, не вызывает внешние API и не сохраняет данные. Необходимые значения передаются явно; HTTP-контекст и глобальное изменяемое состояние не становятся скрытыми источниками условий.

При EF Core используется интеграция `Ardalis.Specification.EntityFrameworkCore`: спецификация применяется к запросу средствами библиотеки, например `WithSpecification`, либо через поддерживающий спецификации репозиторий. Спецификации не требуют обязательного создания нового слоя репозиториев, если существующий доступ к данным уже достаточен. См. [применение к DbContext](https://specification.ardalis.com/usage/use-specification-dbcontext.html).

Фильтрация, которая должна выполняться в БД, задаётся до материализации. Нельзя загружать весь набор через `ToList` или переводить его в `AsEnumerable` ради выполнения удобного, но непереводимого фильтра. Нельзя считать `Compile()` заменой SQL-предиката.

Логика фильтрации переиспользуется в получении списка, подсчёте и проверке существования там, где требуется одинаковый набор. Пагинация списка не должна случайно ограничивать подсчёт всех подходящих записей. Обязательные ограничения области доступа не становятся отключаемым пользовательским фильтром.

Проекция задаётся итоговой спецификацией подходящего типа, например `Specification<T, TResult>`. Сортировка и пагинация применяются явно. Для постраничного чтения нужен определённый порядок, включая правило разрешения одинаковых значений сортировки; конкретные поля и размеры страниц остаются вне стандарта.

## Проверка соблюдения

Unit-тесты проверяют независимые условия и их сочетания: границы, отсутствие необязательного параметра, корректную AND/OR-семантику. Проверка в памяти не доказывает перевод в SQL.

Integration-тесты выполняют итоговые спецификации на используемом провайдере: фильтрация, сочетания условий, подсчёт без пагинации, порядок, проекция и отсутствие обхода обязательных ограничений. Переиспользуемый фильтр не должен неожиданно менять другие части запроса.
