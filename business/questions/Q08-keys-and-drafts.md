## Блок 7. Схемы: ключи, черновики и нумерация
Блок возвращает обсуждение к ContentModeling после уточнений SDK и доставки. Ниже сохранены формулировки вопросов и принятые ответы пользователя от 30.09.2026. Номера 1–6 относятся к этому файлу; ответы 7–8 находятся в [Q09](Q09-editing-and-deletion.md). Ключи экземпляров и полный жизненный цикл их версий будут разобраны отдельно; ответы о схеме не распространяются на них автоматически.
До блока уже были приняты: все определённые в CM типы полей; переход «черновик → опубликовать»; неизменяемость опубликованного содержимого; новая версия на основе предыдущей либо с чистого листа; строгая последовательность публикации; серверная генерация ID новых полей. Ответы ниже дополнительно отменяют пользовательский выбор major/minor и ограничение единственного Draft как целевые правила.
### 1. Кто задаёт ключ схемы и ключи полей?
Например, название схемы — «Карточка экспоната», её ключ — `exhibit`; название поля — «Название», ключ — `title`. Специалист вводит ключи явно или CM предлагает их на основании названий и позволяет исправить перед сохранением? Для схемы и поля правила могут различаться.
Это смысловые ключи, не GUID: ID новых объектов и полей по-прежнему создаёт сервер. Точные правила допустимых символов и роль ключей во внешнем JSON этим вопросом не назначаются.
**Ответ:** Сейчас специалист задаёт ключ схемы и ключи полей явно отдельным вводом. Для Demo действующее правило формата — `camelCase`. Цель MVP — перейти на `kebab-case` и добавить механизм, который по русскому названию предлагает ключ; предложение не отменяет отдельного смыслового поля ключа и должно оставаться контролируемым специалистом.
### 2. В какой области ключ должен быть уникальным?
Нужно ли запрещать одинаковый ключ у двух разных логических схем во всём CM? Версии одной и той же схемы здесь не считаются разными схемами.
Для полей достаточно уникальности среди соседей одного объекта или ключ должен быть уникальным во всём дереве конкретной версии схемы? Например, допустимы ли одновременно `exhibit.title` и `author.title` внутри двух разных вложенных объектов одной структуры?
**Ответ:** Ключи полей обязаны быть уникальны во всём дереве одной версии схемы, а не только среди соседей. Поэтому два поля с одним и тем же ключом в разных вложенных объектах одной версии недопустимы. Глобальная область уникальности `EntitySchema.Key` между разными логическими схемами этим ответом не определена и остаётся отдельным уточнением.
### 3. Когда можно менять уже заданный ключ?
Можно ли исправлять ключ схемы до первой публикации и после неё? Для поля опубликованное определение не редактируем: вопрос в том, можно ли в следующем черновике переименовать его ключ, сохранив смысл «это то же поле», или такой шаг должен считаться удалением старого поля и добавлением нового.
Изменение отображаемого названия не приравнивается к смене ключа. Автоматические алиасы, перенос данных и преобразование клиентских моделей этим вопросом не добавляются.
**Ответ:** Ключ логической схемы можно менять и после первой публикации. **Решение блока 8 отменяет прежнюю изменяемость ключа поля:** для существующего `SchemaFieldId` `Key` и `FieldDataType` неизменяемы. Для другого key/type/бизнес-смысла старое поле исключается из новой версии, а новое получает новый ID. Опубликованные версии при этом не переписываются; как rename самой схемы отражается на старом lookup, JSON Schema и generated models, уточняется в Q31.
### 4. Сколько черновиков одной схемы может существовать одновременно?
Разрешаем только один общий редактируемый черновик схемы или несколько будущих версий в подготовке? Например, один специалист готовит небольшое изменение, а другой — следующую большую структуру той же схемы.
Ограничение «один Draft» присутствует в переданном коде, но его сохранение как бизнес-правила ещё не принято. Возможность нескольких черновиков не означает Git-подобные ветки или автоматическое объединение; строгий порядок публикации сохраняется.
**Ответ:** Одновременно можно готовить несколько Draft-версий одной схемы. Текущее ограничение домена «один Draft» не является целевым бизнес-правилом и требует изменения. Git-подобное ветвление/merge из этого не следует; порядок выбора и разрешение конфликтов между параллельными Draft при публикации ещё уточняются.
### 5. Как специалист выбирает номер следующей версии схемы?
В текущей модели есть major/minor-нумерация. Сохраняем два действия «следующая minor» и «следующая major», после которых сервер сам рассчитывает номер? Если да, по какому понятному правилу специалист выбирает между ними? Или для Demo нужно одно действие «создать следующую версию» без такого выбора?
Примеры `1.1`, `1.2`, `2.0` иллюстрируют вопрос, а не назначают начальный номер. Номер версии не означает автоматическую поддержку её клиентом; автоматический анализ совместимости сюда не включается.
**Ответ:** Специалист не вводит номер и не выбирает `major`/`minor`. В интерфейсе одно действие — «создать следующую версию»; система создаёт новый Draft с собственной технической идентичностью. Формат опубликованного номера и алгоритм его следующего значения уточняются отдельно, но пользователь не назначает номер вручную.
### 6. В какой момент закрепляется номер и что происходит после удаления черновика?
Номер присваивается при создании черновика или только при публикации? Если черновик получил номер, но был удалён без публикации, разрешено ли использовать этот номер для следующего черновика или номер остаётся пропущенным?
Опубликованные номера не перенумеровываем и старое состояние не подменяем. Вопрос относится только к непубликовавшейся работе и не отменяет строгого порядка публикации. Физическое удаление истории и остальные сценарии удаления относятся к Q09, а не определяются ответом о нумерации.
**Ответ:** Бизнес-номер версии закрепляется только при публикации. Draft до публикации идентифицируется своим `SchemaVersionId`, поэтому удаление неопубликованного Draft не «съедает» номер и не создаёт пропуск в опубликованной последовательности. При нескольких Draft следующий номер получает тот Draft, который фактически проходит публикацию; правила конфликтов устаревшей базы ещё нужно детализировать.

## Блок 23. Параллельные Draft, stale-base и конкурентная публикация
### Published baseline Schema Draft
Каждый `EntitySchemaVersion` Draft хранит `BasePublishedVersionId` — Published-версию той же EntitySchema, относительно которой начата authoring-работа.
- если Published ещё нет — `null`;
- новый Draft от текущей Published vN → base=vN;
- clean Draft при существующей latest Published всё равно получает её как baseline;
- Draft, скопированный из другого Draft, наследует его `BasePublishedVersionId`.
Отдельная source-Draft identity не участвует в lifecycle/stale инварианте. При необходимости provenance «откуда скопировано» может храниться отдельно и не заменяет baseline.
Draft stale, если его `BasePublishedVersionId` не совпадает с current latest Published SchemaVersionId. Stale — вычисляемое состояние, не отдельный persisted lifecycle status.
Stale Draft можно читать, редактировать и сохранять, но нельзя Publish.
### Разрешение stale-base
Automatic merge/rebase schema tree отсутствует.
При Publish stale Draft сервер возвращает предметный conflict. UI показывает baseline и current Published и semantic diff: added/removed fields, изменения Name/Required/Deprecated/options и другие contract changes.
Специалист может:
1. создать новый Draft от current Published и вручную перенести нужные изменения; либо
2. выполнить явное действие **«Актуализировать основу»**.
«Актуализировать основу» не меняет Content Draft и не выполняет merge. Сервер повторно валидирует Draft относительно current Published по всем evolution-инвариантам. Если проверка проходит, `BasePublishedVersionId` становится current Published. Если нет — действие отклоняется до ручного исправления Draft.
После актуализации Draft снова publishable, пока current Published не изменится повторно.
### Конкурентный Publish
Если несколько Draft имеют одну baseline, только один concurrent publish может стать следующей Published version.
Победитель атомарно проверяет baseline, strict validation, назначает следующий business VersionNumber, hash/PublishedAt и фиксирует Published state.
Остальные concurrent attempts после commit победителя получают stale-base conflict. Они **не становятся следующими версиями автоматически**.
### Published numbering
`EntitySchemaVersion.VersionNumber` — положительный монотонный integer: `1, 2, 3...`.
Draft business number не имеет. Номер назначается только при успешном Publish, никогда не переиспользуется и не меняется.
Для `EntityInstanceVersion` действует тот же формат `1, 2, 3...`, но sequence отдельная на каждый EntityInstance и уже согласованно общая для всех его SchemaVersionId.
### EntitySchema.Key
`EntitySchema.Key` глобально уникален среди логических EntitySchema Content Manager.
Rename разрешён и после первой публикации, если новый key свободен. Освободившийся старый current key не резервируется навсегда и потенциально может быть использован другой схемой.
Published SchemaVersion остаётся immutable contract snapshot и сохраняет schema key/name contract metadata, актуальные на момент её публикации. Последующий rename логической EntitySchema не переписывает старые Registry/codegen contracts.
### EntityInstance stale-base
Для Draft EntityInstanceVersion baseline определяется **внутри target SchemaVersionId**.
Draft хранит `BasePublishedInstanceVersionId` — latest Published EntityInstanceVersion того же EntityInstance для той же target SchemaVersion на момент создания; если такой версии нет — `null`.
Если Draft создаётся copying из другой SchemaVersion, source используется только для переноса данных по SchemaFieldId, а baseline определяется по target SchemaVersion.
Публикация версии экземпляра по другой SchemaVersion не делает Draft stale. Публикация более новой версии по той же target SchemaVersion делает его stale.
Stale Instance Draft можно Save, но нельзя Publish. Разрешение такое же: создать новый Draft либо явно актуализировать baseline без автоматического merge после server validation.
`SchemaVersionId` существующего EntityInstanceVersion Draft после создания неизменяем. Для другого target создаётся новый Draft, при необходимости на основе текущего.
### Optimistic concurrency
Stale-base и concurrent edit — разные проверки.
Все mutable CM aggregate/state, где возможны конкурентные записи, используют отдельный внутренний `int Version` как optimistic-concurrency token.
- read model/DTO возвращает current `Version`;
- mutation передаёт `ExpectedVersion`;
- successful mutation атомарно увеличивает `Version`;
- mismatch даёт concurrency conflict;
- last-write-wins и automatic merge запрещены.
Publish проверяет одновременно current Draft `Version` и Published baseline. Поэтому нельзя опубликовать содержимое, изменённое после того, как пользователь его загрузил.
Для VR School projections source snapshot number хранится отдельно как `SourceVersion`; внутренний CM `Version` не заменяет source freshness.
`Version` не является Published `VersionNumber` и не является activation `Sequence`.
