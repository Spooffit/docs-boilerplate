# F07. Общий контент Product

## Цель

Позволить специалисту определить общий рабочий набор контента Product, который будет наследоваться его ProductVariant при последующей публикации.

ProductContentAssignment является рабочим состоянием подготовки. Сохранение не означает готовность release или публикацию клиентского состава.

## Участники и границы

Редактирование выполняет специалист Content Manager. Product создаётся и изменяется в VR School; Content Manager не редактирует исходные поля каталога.

Само сохранение assignment не создаёт release, не строит итоговую ProductVariant revision, не активирует контент и не меняет Delivery. Отдельный явный мастер «Подготовить выпуск» координирует эти существующие операции в согласованном порядке. Полный Product Publishing относится к MVP; авторизация не становится скрытой зависимостью Demo.

## Состав assignment

Product хранит назначения схем с явно выбранной exact Published SchemaVersion и политикой выбора экземпляров. Схема является первым уровнем дерева, экземпляры — вторым. Назначение не делает схему эксклюзивной собственностью Product. Для каждого логического EntityInstance в разрешённом составе допускается не более одной exact версии; matching использует stable IDs, а не переименовываемые keys.

| Режим | Рабочее правило | Подготовка нового release |
| --- | --- | --- |
| Все экземпляры | AllExcept без исключений | Последняя Published версия каждого экземпляра внутри выбранной SchemaVersion |
| Все, кроме выбранных | AllExcept с excluded EntityInstanceId | То же, за вычетом исключённых IDs |
| Только выбранные | SelectedOnly с exact включениями | Сохраняет явно выбранные версии без автоматической замены |

Новый Published экземпляр включается AllExcept при подготовке следующего release, но не меняет existing releases/revisions. Новая версия структуры не выбирается автоматически. Перед Create пользователь подтверждает конкретный разрешённый набор; изменение состава после review требует нового подтверждения. Для AllExcept winner — максимальный Published VersionNumber внутри target; его недоступность блокирует release, а не вызывает silent fallback/skip. Draft-only объекты отображаются отдельно и не входят в Published composition. Полные границы и инженерные вопросы — [Q39](../questions/Q39-schema-content-selection.md).

Назначение схемы с нулём экземпляров не удаляется автоматически. AllExcept с нулём результатов и SelectedOnly с пустым выбором различаются поведением при новых публикациях. Ручной порядок не вводится.

Новый selector требует допустимую exact Published SchemaVersion. Новое exact включение/замена требует допустимую Published InstanceVersion по этой структуре. Draft, Retired, Withdrawn и unavailable reference нельзя добавить как новый pin. Автоматическое разрешение instance version допускается только явной политикой AllExcept на этапе подготовки release; в остальных случаях система не подставляет latest.

## Основной сценарий

1. Специалист открывает Product Workspace и видит дерево назначенных схем, режим, exact версию структуры, счётчики и диагностику.
2. Добавляет схему, явно выбирает Published SchemaVersion и режим AllExcept/SelectedOnly.
3. При необходимости раскрывает схему, отмечает исключения либо exact включения, меняет режим с видимым diff или удаляет назначение схемы.
4. Сохраняет структурно корректное рабочее состояние.
5. Отдельно проверяет готовность создания ProductRelease по F09 и устраняет его blockers.

## Массовая фиксация и подготовка выпуска

Пользователь не обязан открывать каждую схему и экземпляр для фиксации. В списках схем и экземпляров предусмотрено отдельное действие «Зафиксировать выбранные версии», а в «Каталог и публикации» — мастер «Подготовить выпуск». Это целевой workflow, а не утверждение о готовности текущего кода; exact transport и долговременное выполнение уточняются в [Q38](../questions/Q38-bulk-version-freeze-and-release-preparation.md).

Мастер принимает явно выбранные exact Draft IDs и уже Published references, показывает необходимые Draft схем и экземпляров, текущие concurrency tokens, validation/stale-base/lifecycle blockers и итоговый продуктовый состав. Не выбирает `latest`, не фиксирует черновики при обычном Save и не меняет выбор без подтверждения. Для одного logical owner/target нельзя скрыто выбрать победителя из нескольких конфликтующих Draft.

После preflight и явного подтверждения сначала фиксируются необходимые SchemaVersion по F03, затем выбранные EntityInstanceVersion по F04. Полученные exact Published IDs используются для assignment; далее выполняются существующие F09 release и F10 revision операции. Для Variant сохраняются правила F08 overrides/exclusions и явного выбора source releases; мастер не обходит их. Перед каждым шагом повторяются актуальные guards. Изменение проверенных входов требует повторной проверки и подтверждения.

Предварительная проверка всего набора не является общей транзакцией между BC. Если часть версий уже зафиксирована, а следующий шаг отклонён, созданные immutable версии остаются и показываются в поэлементном результате; они не откатываются в Draft. Продуктовая стадия начинается только после успешной фиксации всего подтверждённого набора. Частичный результат не объявляется готовым выпуском, а активная ревизия не меняется. Повтор использует подтверждённые результаты и перечитанные exact состояния, не повторяет неизвестную запись вслепую.

Создание revision не заменяет F17 moderation, F11 activation и Delivery readiness. Эти шаги показываются отдельно; «Подготовлен выпуск» не означает «Выдаётся клиентам». Массовая фиксация ContentModeling может использоваться самостоятельно без полного Product Publishing и не добавляет его в Demo.

UI различает «Зафиксировать версию» (сохранить immutable Published SchemaVersion/InstanceVersion) и продуктовый выпуск. Технические HTTP операции Publish и enum `Published` от смены подписи не переименовываются.

## Порядок состава

Assignment/release/revision не содержат редактируемого пользователем «Порядка в релизе» или SortOrder. Состав является набором exact references; стабильный порядок сериализации определяется canonical profile F10/Q19 на сервере. Локальная сортировка таблицы не меняет состав или хеш. ReleaseNumber, activation Sequence и authored порядок элементов List в самом контенте сохраняют собственный смысл. Если приложению нужна последовательность уроков/сцен, она явно моделируется в контенте, а не в назначении.

## Save и доступность references

Сохранение других изменений разрешено, если ранее выбранная exact reference осталась неизменной, даже когда её version стала Retired/Withdrawn, logical owner был Archived либо dependency стала unavailable. Reference сохраняется под теми же IDs и показывается с причиной недоступности. Она блокирует создание нового release до удаления или замены допустимой reference.

Сохранённая недоступная reference не считается повторным новым использованием. Добавление новой позиции, повторное добавление удалённой позиции и замена exact version всегда проверяются как новое использование. Изменение локальной сортировки отображения неизменной позиции не является новым использованием. Нельзя перенести недопустимую reference в новую позицию, прикрыв это сохранением старого набора.

Удаление проблемной reference либо её замена допустимой разрешены. Для Archived Product допускается ограниченное сопровождение: сохранение неизменных exact refs, удаление позиций и замена проблемных references допустимыми. Добавление позиций и расширение набора не разрешаются; intrinsic/new-use/scope guards сохраняются. Source Active/Archived, ограничения parent и restore определяются F06.

Открытый блокирующий CatalogConflict F15 запрещает обычные изменения affected assignment, включая удаление и замену. Ограниченное сопровождение Archived owner не даёт обхода conflict. Начальный отдельный corrective repair F15 относится только к working Variant patch; Product assignment repair требует отдельно спроектированного действия либо source correction в VR School.

## Диагностика и готовность release

Система различает:

- **SaveBlockers** — ошибки собственной структуры, недопустимое новое использование, запрет операции для owner, доступ/конкуренция и открытый блокирующий conflict;
- **ReleaseBlockers** — сохранённые недоступные exact references или зависимости, запрещающие новый release;
- **Warnings** — разрешённые предупреждения, например Deprecated reference, если текущая policy допускает её использование.

Дубликаты logical EntityInstance, неправильная identity и другие intrinsic ошибки структуры блокируют Save. ReleaseBlockers не отменяют успешный Save допустимого рабочего состояния. UI отдельно показывает «Сохранено», диагностику и CanCreateRelease; «Сохранено» не означает «Можно создать release».

Диагностика зависит от текущих внешних данных отдельно от версии самого assignment/его ETag. Неизменный assignment не гарантирует неизменную доступность dependencies. Ошибка чтения нужных данных не превращается в пустую диагностику или разрешение release.

## Удаление и история

Удаление позиции меняет только будущий рабочий Product composition. Assignment не является историей: историческая фиксация начинается с F09 release.

Save, замена и удаление не переписывают существующие ProductRelease/PublicationRevision и historical Delivery. Недоступность не вызывает автоматическое удаление reference, выбор latest или пересчёт истории.

## Результат

Сохранён mutable ProductContentAssignment с точными references и отдельной оценкой готовности создания immutable ProductRelease.

## Acceptance

- назначение схемы показывает fixed Published структуру и «Все», «Все, кроме» либо «Только выбранные»; выбор экземпляров доступен внутри дерева;
- новый Published instance в target учитывается AllExcept при следующем release review, но не попадает в SelectedOnly и не меняет historical release;
- AllExcept исключает stable IDs независимо от будущих версий этих объектов; новый SchemaVersion не подключается автоматически;
- пустая схема остаётся назначенной; own rule ETag и current resolved preview различаются.

- exact допустимая Published version добавляется; Draft/Retired/Withdrawn/unavailable version в новой позиции или замене отклоняется;
- если сохранённая A/v2 стала Retired, можно сохранить добавление допустимой B/v1, оставив A/v2: Save успешен, диагностика блокирует release;
- локальная сортировка отображения A/v2 не меняет assignment/new-use; удаление A/v2 и её последующее добавление требует полной текущей eligibility;
- unavailable A/v2 можно удалить или заменить допустимой A/v3 без автоматического latest;
- Archived Product допускает неизменные refs, удаление и замену проблемной reference, но не добавление B; открытый blocking conflict запрещает и эти ordinary mutations;
- две версии одного logical EntityInstance блокируют Save как intrinsic duplicate;
- успешный Save и CanCreateRelease различимы; failed dependency read не показывает пустой валидный результат;
- изменение рабочего набора не меняет existing releases/revisions и не публикует контент клиентам.
