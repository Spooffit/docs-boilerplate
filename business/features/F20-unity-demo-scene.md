## Цель, участники и этап

Команда CM создаёт небольшую тестовую Unity-сцену для демонстрации получения и синхронизации контента команде Unity-разработчиков. Сцена является отдельным обязательным результатом Demo, а не частью функциональной ответственности клиентской библиотеки.

По решению пользователя исходная общая F19 разделена: библиотека остаётся в F19, сцена описывается в F20. Разделение не отменяет ни одну из функций Demo и не вводит новые требования к графическому оформлению.

## Границы и зависимости

Сцена использует публичный интерфейс F19. Общий HTTP-контракт и серверный расчёт изменений остаются в F13. Не создавать собственный обходной HTTP-клиент или повторный серверный алгоритм внутри сцены.

Выбрана самостоятельная сцена «Каталог экспонатов»: список по двум точным версиям схемы, подробности выбранного элемента, изображение, контекст и управление синхронизацией. Интерфейс uGUI + TextMeshPro, изображение в RawImage; первый Player — Unity 2022.3.62f3 Windows x64/IL2CPP с мышью и клавиатурой. Сцена поставляется отдельным samples/UnityDemo проектом внутри SDK-репозитория и использует packages по Q32. Библиотека может использоваться без сцены. Интеграция в существующий музей, лаунчер или VR-продукт не требуется.

В Demo нет авторизации, лицензирования, шины, интеграции с VR School, административного согласования и полного Publishing. Образцы внешнего окружения допустимы, но фактическое получение контента и загруженного в CM изображения не заменяется встроенными фиктивными значениями.

## Основной демонстрационный сценарий

1. Команда CM готовит fixture через F01–F05, получает exact generated модели через F22 и настраивает адрес CM/клиентский контекст в Inspector. Две версии схемы явно зарегистрированы в коде по generated metadata.
2. При запуске сцена читает ранее сохранённые committed данные через F19; обязательного auto-sync нет.
3. По кнопке «Синхронизировать» выполняется initial sync двух exact версий. Показаны реальные опубликованные данные и отдельно загруженное изображение.
4. В CM создаётся новый Draft: повтор sync сохраняет прежнее Published содержимое.
5. Publish изменения и следующий sync показывают Update; публикация нового экземпляра показывает Add; Withdrawal опубликованного экземпляра — Remove.
6. Две exact representations одной logical entity видны независимо и не вытесняются по одному InstanceId.
7. После перезапуска committed данные сохранены; без сети они остаются читаемыми, а загрузка изображения может завершиться отдельной ошибкой.
8. Stop и последующее продолжение проверяются отдельно от Discard незавершённой попытки. Lost ACK и crash recovery проверяет управляемый стенд, без имитации сервера в обычной сцене.

Сцена не создаёт серверный контент; оператор готовит данные существующими административными операциями.

## Набор демонстрационных данных

Основная схема — `demoExhibit`, тема — небольшой каталог экспонатов. Команда CM подготавливает две Published версии этой схемы и опубликованные экземпляры для обеих exact групп. Во второй версии добавлено поле и одно существующее поле помечено deprecated; сохраняющиеся поля сохраняют identities. Точные server-generated IDs записываются при подготовке, не назначаются из примеров.

| FieldDataType | Field Key | Назначение в fixture |
| --- | --- | --- |
| String | `title` | Название экспоната |
| Text | `description` | Описание по принятому sanitized HTML контракту; сцена показывает текст без исполнения HTML |
| Integer | `catalogNumber` | Целое число; edge fixture включает значение больше 2⁵³ в допустимом диапазоне Integer |
| Float | `weight` | Конечное дробное значение |
| Decimal | `estimatedValue` | Точное десятичное значение |
| Boolean | `featured` | Обычное значение, включая сохранённое false |
| DateTime | `recordedAt` | Naive DateTime по Demo-контракту |
| Date | `acquiredOn` | Дата без времени |
| TimeSpan | `presentationDuration` | Длительность, включая отрицательное значение в edge fixture |
| Enum | `category` | Immutable wire key объявленной опции |
| FlagEnum | `tags` | Набор объявленных опций, включая пустой |
| Color | `accentColor` | Цвет по согласованному wire-контракту |
| Object | `location` | Вложенные значения |
| List | `relatedExhibits` | `List<Object>` |
| AssetReference | `image` | Ссылка на реальное загруженное изображение |

Дополнительное поле `measurementRows` типа List покрывает `List<List<…>>`. Keys вложенных полей уникальны во всём дереве версии по [Q34](../questions/Q34-schema-field-semantics.md). Типы, required/missing semantics и ограничения берутся из Q34 и Published definition; таблица задаёт содержимое fixture, не второй DTO/serializer contract.

Минимальные случаи: обычный заполненный экспонат с изображением; допустимые отсутствующие optional поля, false, нули и пустые коллекции; Unicode, числовые границы и вложенные списки. Дополнительные references на реальные загруженные Audio/Video assets покрывают модели и сериализацию; воспроизведение аудио/видео в F20 не требуется. Text fixture также используется для sizing configured cap.

Подготовка проходит через публичные операции CM F01–F05. После публикации команда получает модели через F22, добавляет их в проект сцены и сохраняет воспроизводимую инструкцию подготовки с соответствием фактических exact IDs. При пересоздании fixture с новыми IDs модели и конфигурация обновляются вместе. Встроенные данные, seed SQL и прямые записи в серверную БД не заменяют этот приёмочный путь.

## Правила показа

Controls сцены: «Синхронизировать», «Остановить», «Отбросить незавершённую попытку», «Повторить загрузку изображения». Доступность следует состоянию SDK; Stop/Discard получают handle конкретной попытки. Запуск sync явный, повтор image не запускает sync. Кнопки очистки базы нет. Момент sync в остальных приложениях выбирает приложение, не библиотека F19.

Нужен видимый результат запроса и различение успешного обновления, отсутствия изменений и ошибки. Частичное получение нельзя выдавать за полностью завершённый показ согласованного результата.

По F19 данные применяются целыми exact schema/version groups; между группами допустим явно показанный частичный результат. Установка данных, проверка актуальности и отдельная загрузка изображения имеют разные исходы. Ошибка изображения не отменяет successful data commit, но успешная установка сама не подтверждает полноценный показ изображения или актуальность всего состава.

Выбран первый Windows x64/IL2CPP Player Unity 2022.3.62f3; exact patch, stripping/build settings, package/native locks и backend окружение фиксируются до spike по Q32. Показ включает все 15 типов, две exact версии, nested Object/List/List<List> и реальное изображение. Поля сопоставлены с generated models явно; scalars отображаются текстом, Object/List — структурированными строками. Поддержка типов подтверждается отдельными conformance tests, а не только видом карточки.

Сцена использует SQLite adapter через F19; файл находится в выделенной папке под Application.persistentDataPath, разделённой по клиентскому контексту. Путь переопределяем для проверок; native/AOT compatibility должна быть доказана. Конфигурация — ScriptableObject в Inspector, фиксирована на время запуска. Registry задаётся кодом по generated metadata; автоматического latest и runtime-редактора registry нет. Несовпадение fixture, моделей и конфигурации — ошибка подготовки.

После sync сцена перечитывает committed данные, сохраняет выбор по exact representation identity, если она осталась; при Remove очищает подробности/изображение. При partial видны применённые целые группы и прежнее состояние остальных. Изображение загружается только для выбранного элемента; прежний owned handle освобождается при смене. Ошибка image не откатывает данные.

## Критерии приёмки

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Сцена подключена к CM через F19 | Взаимодействие проходит через публичную библиотеку |
| Первичное получение | Показаны реальные опубликованные данные из CM |
| Изображение загружено в CM и использовано в данных | Получено и показано именно это изображение |
| В CM сохранён новый Draft | Клиентское отображение опубликованного содержимого не меняется на черновик |
| Версия опубликована | Следующая синхронизация отражает обновление нужного представления |
| Экземпляр добавлен или снят с выдачи | Представление появляется или убирается согласно серверному ответу |
| Запрошены две версии одной схемы | Видно, что разные структуры могут использоваться независимо |
| Возникла ошибка получения | Нет ложного full success; раздельно показаны итог данных, актуальность и ошибка изображения |
| Fixture содержит все 15 типов, nested Object/List и две exact версии | Schema/instance/Registry/generated C#/SDK проходят согласованный round-trip; версии представлены независимо |
| Приложение перезапущено после обрыва / потерян server ACK | Продолжение использует durable состояние; группа не применяется повторно из-за lost ACK |
| Старт и перезапуск без сети | Ранее committed данные видны без auto-sync; ошибка image отделена от читаемости данных |
| Удалён выбранный элемент / частичный результат | Выбор привязан к exact identity; удалённые подробности/изображение очищены, неполные группы сохраняют прежние данные |
| Поставка и управление | uGUI/TextMeshPro/RawImage, мышь/клавиатура; реальные packages и Windows x64 IL2CPP Player |
| Stop либо Discard | Stop сохраняет resume; Discard очищает незавершённую попытку и сохраняет committed groups |
| Withdrawal во время sync | Неполная affected group не применяется; committed state сохраняется, следующий план отражает снятие |
| После старого плана опубликовано изменение | Freshness явно сообщает update available; failure проверки остаётся unknown |

Приёмка проходит в настоящем Unity 2022.3.62f3 Windows x64 IL2CPP Player с установленными SDK packages, generated моделями, SQLite и реальным CM + PostgreSQL + YARP/private S3-compatible storage. Scene doubles проверяют только presentation. Критерии описывают будущую проверку; показ, Player/native и сеть здесь не запускались. Сцену и SDK можно принимать отдельно, это не доказательство готовности интеграций MVP. Launcher/shared persistent media cache/selective preload/RequiredBeforeLaunch относятся к этапу после самостоятельного Demo по [F19](F19-unity-client.md#launcher-и-общий-media-cache-после-demo) и не являются зависимостями этой сцены.
