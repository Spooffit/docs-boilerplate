# Компонентное тестирование с bUnit

**Применяется к:** Blazor-проектам, сознательно использующим bUnit. Профиль выбирает тестовую библиотеку, а не конкретную модель рендеринга или производственный набор UI-компонентов.

## Что доказывает компонентный тест

bUnit рендерит Razor-компоненты в тестовом контексте, подаёт параметры и сервисы, инициирует события UI и исследует разметку или видимое поведение. Он не заменяет настоящий браузер, backend и полный пользовательский сценарий.

- Предпочитайте утверждения о видимом состоянии, отключённых элементах, сообщениях, навигации и callback, а не о приватных полях компонента.
- Проверяйте загрузку, валидацию, ошибки, отмену, пустые состояния и интерактивные переходы, принадлежащие компоненту.
- Используйте управляемые подмены на границах HTTP/клиента и зависимостей; фальшивый ответ не подтверждает живой API-контракт.
- Создавайте новый или намеренно изолированный тестовый контекст для случаев с изменяемыми сервисами.
- Освобождайте отрендеренные компоненты и фикстуры, чтобы callback или таймеры не перетекали между тестами.

## Устойчивые изолированные компонентные тесты

- Готовьте ввод и необходимые подмены в новом тестовом контексте bUnit с независимым освобождением. Передавайте параметры, cascading values и только необходимые сервисы; не делите изменяемое состояние renderer/DI между параллельными тестами.
- Вызывайте обычные события компонента, такие как click, change и submit, либо его реальный публичный callback, а не приватные обработчики напрямую. Проверяйте значимые тексты, подписи, disabled, параметры, запросы и callback; не привязывайтесь к внутренним полям, количеству render или CSS-классам фреймворка.
- Используйте семантический `MarkupMatches` на нужном фрагменте для сравнения HTML. Снимки огромного дерева сторонних компонентов не заменяют проверку поведения. Подменяйте дочерний компонент только для намеренно изолированного поведения родителя; это не доказывает композицию с настоящим ребёнком.
- Настраивайте ожидания bUnit JS interop явно и предпочтительно строго проверяйте необходимые вызовы. Подмена `IJSRuntime` подтверждает обращение .NET к JavaScript, но не реальное исполнение браузерного JS, DOM или layout.
- Для асинхронного рендера используйте `WaitForAssertion` или `WaitForState` с ограниченными тайм-аутами. Не помещайте click/submit/изменения внутрь повторяемого assertion. Управляйте завершением задач для проверки загрузки, ошибки, отмены, повторных действий и устаревших ответов вместо произвольных sleep.
- Подменённый API-адаптер или `HttpMessageHandler` проверяет клиентские запросы компонента; самому адаптеру нужны отдельные тесты реального транспорта/сериализации, а настоящему UI с сервером — интеграционные или E2E-проверки.

Источники: [bUnit: асинхронные проверки](https://bunit.dev/docs/verification/async-assertion.html), [bUnit: JS interop](https://bunit.dev/docs/test-doubles/emulating-ijsruntime.html).

## Размещение тестов с учётом архитектуры

Если проект **выбрал Feature-Sliced Design (FSD)**, размещайте тесты рядом с владельцем поведения UI: Shared для примитивов, Entities для отображения/состояния, Features для взаимодействий, Widgets для композиции, Pages для маршрутизации и App для providers/bootstrap. Проверяйте *реальные* публичные зависимости и границы slices в архитектурных тестах; не навязывайте FSD каждому Blazor-проекту. Тестовые builders оставляйте в тестовых проектах, не в производственном Shared.

Компонентный тест с подменённым API остаётся компонентным, даже если рендерит несколько реальных дочерних компонентов. Тест HTTP-адаптера клиента имеет другой SUT, а путь через несколько приложений с реальными сервисами может быть E2E. Проверяйте только действительно исполняемую границу. Именование выбирает проект; имена по наблюдаемому поведению — нейтральное значение по умолчанию, а не обязательный `MethodUnderTest_Scenario_ExpectedBehavior`.

Источник: [слои FSD](https://feature-sliced.design/docs/reference/layers), [публичный API FSD](https://feature-sliced.design/docs/reference/public-api).

## Браузер и отдельно размещённый UI

Реальные браузерные тесты (например, Playwright для .NET) нужны для того, что bUnit не исполняет: фокус, клавиатура, JS-зависимые элементы, deep-link/reload, скачивание, загрузка статических ресурсов, сетевые credentials, настоящие CORS/cookies/CSRF и взаимодействие UI/API на разных origin. Браузер с замоканным API **не доказывает**, что живой контракт backend работает.

Предпочитайте устойчивые локаторы role/name/label или test-ID вместо DOM-индексов и sleep. Используйте автоматическое ожидание доступности действий и повторяемые *чистые* assertions. Параллельным тестам предоставляйте изолированные контексты браузера и данные. Собирайте безопасную диагностику ошибок без утечки секретов. Реальные браузеры, топологию, раннер и бюджет тестирования выбирает проект.

Источники: [Playwright .NET: локаторы](https://playwright.dev/dotnet/docs/locators), [автоожидание](https://playwright.dev/dotnet/docs/actionability), [проверки](https://playwright.dev/dotnet/docs/test-assertions).

## Совместимость с раннером

Проверяйте совместимость bUnit с фактическим фреймворком и раннером. Документированные интеграции bUnit включают xUnit, NUnit и MSTest; **не предполагайте поддержку непроверенной интеграции с TUnit лишь потому, что TUnit работает на MTP**. Проверяйте конкретные версии пакетов и запускайте компиляцию/пример теста.

## Дополнительные проверки

Используйте браузерное тестирование для реальной клавиатуры, фокуса, CSS/layout, JavaScript interop, клиентских маршрутов и настоящей сети. Компонентные тесты и E2E имеют разные области действия.

Источники: [bUnit: написание тестов](https://bunit.dev/docs/getting-started/writing-tests.html), [жизненный цикл Blazor](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/lifecycle?view=aspnetcore-10.0).
