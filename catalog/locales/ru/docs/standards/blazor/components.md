# Компоненты Blazor и состояние интерфейса

**Применяется к:** проектам, явно использующим Blazor (interactive server, WebAssembly, hybrid или static SSR в соответствии с фактическим выбором).

## Состояние и жизненный цикл компонентов

- Различайте инициализацию, изменения параметров, рендеринг и освобождение ресурсов. `OnInitializedAsync` не всегда подходит для повторной загрузки при изменении маршрута или параметров компонента; при необходимости используйте `OnParametersSetAsync`.
- До ожидания незавершённых задач сохраняйте состояние компонента пригодным для рендеринга.
- Отменяйте длительные операции при уничтожении или замене компонента. Не позволяйте устаревшему ответу перезаписать новое состояние UI.
- Освобождайте подписки, таймеры и ресурсы отмены. Не обновляйте уже уничтоженные компоненты.
- Выбирайте хранение устойчивого состояния (URL, scoped service, браузерное хранилище или сервер) исходя из реальных потребностей; не храните секреты в доступном браузеру состоянии.

## Взаимодействия и границы API

- Различайте локальное состояние формы, отправленный запрос, принятую сервером операцию и сохранённый результат. Не показывайте успех раньше подтверждения авторитетного сервера.
- DTO запросов API должны соответствовать принятому HTTP-контракту, но клиентская форма не доказывает наличие серверной авторизации.
- Разделяйте временные отказы и неопределённые исходы записи. Не повторяйте неидемпотентные запросы без проверки.
- Используйте сообщения валидации, доступные вспомогательным технологиям, и корректное управление клавиатурой.

## Рендеринг и производительность

У Blazor разные модели размещения и рендеринга. Не предполагайте одинаковое поведение prerendering, JS interop и авторизации во всех приложениях. При предварительном серверном рендеринге инициализация может выполняться несколько раз. Избегайте неожиданных повторных внешних эффектов.

Сохраняйте устойчивые ключи компонентов при перестановке списков, когда иначе визуальное состояние привяжется к другому элементу. Измеряйте рендеринг и сеть до преждевременного введения state framework или новых компонентов.

## Конкурирующие клиентские операции

Если интерактивный компонент сохраняет данные или загружает информацию для меняющегося выбора, моделируйте локальные правки, ожидающий HTTP-запрос и авторитетный ответ сервера как отдельные состояния. Поздний ответ для старого ресурса не должен перезаписывать новый выбор; отменяйте или помечайте устаревшую работу. Сохраняйте восстановимый ввод при ошибках проверки или сети, если это нужно пользователю.

Для компонентов с HTTP API используйте DTO и метаданные ответа (в том числе необязательный ETag) согласно выбранному контракту. Не создавайте второй источник истины API. Прямая привязка DTO к форме — **отдельно выбираемое** соглашение, а не обязанность Blazor. Проверяйте точный запрос, создаваемый действием пользователя, отдельно от визуального отклика.

## Проверка

Компонентные тесты проверяют поведение UI изолированно (bUnit — необязательный профиль); браузерные тесты — реальный DOM, фокус, сеть и JavaScript. Проверяйте загрузку, пустые состояния, ошибки, отмену и видимые результаты авторизации.
