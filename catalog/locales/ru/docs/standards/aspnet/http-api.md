# Проектирование HTTP API на ASP.NET Core

**Применяется при явном выборе ASP.NET Core HTTP API.** Не навязывает MVC, CQRS, FluentValidation, EF Core или специальные схемы ответов.

## Публичный контракт и транспорт

Описывайте методы, маршруты, значения параметров, nullable, сериализацию, статусы, заголовки и авторизацию по реально принятому контракту. Не выставляйте внутренние сущности как публичную модель без осмысленного решения. Сохраняйте корректность HTTP-семантики.

Границы приложения должны оставаться явными: обработка транспорта отличается от принятия бизнес-решения и фиксации данных. Не размещайте неограниченную логику доступа и записи прямо в транспортном адаптере по умолчанию.

## Асинхронность и отмена

Передавайте CancellationToken только по предусмотренной операции. Отмена HTTP-запроса не доказывает откат уже выполненного изменения. Различайте принятый запрос и завершённую асинхронную работу.

## Конкуренция и условные запросы

Если есть ETag/If-Match, проверяйте серверный валидатор и атомарность вместе с записью. Не считайте курсор или внутреннюю версию сущности ETag без принятого сетевого контракта.

## Статусы и ошибки

Возвращайте значимые коды HTTP, различайте синтаксическую валидацию, авторизацию, отсутствие ресурса, конфликт состояния, ошибку зависимости и внутреннюю ошибку. Не раскрывайте stack trace и приватные данные. Используйте стабильный формат Problem Details, если это действительно принятый API-контракт.

## OpenAPI и совместимость

Проверяйте, что опубликованная спецификация согласована с реальным приложением и сериализацией. Изменения потребительского API оценивайте по настоящим клиентам, не только по сигнатурам C#.

## Проверка

Проверяйте действующие маршруты, статусы, заголовки, тела, отмену, права, несовместимые входные данные, конкуренцию и ошибки через реальный HTTP-пайплайн. Прохождение модульного теста контроллера не доказывает middleware и транспорт.
