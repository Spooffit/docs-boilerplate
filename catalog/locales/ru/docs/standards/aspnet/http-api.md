# Проектирование HTTP API на ASP.NET Core

**Применяется к:** приложениям ASP.NET Core с HTTP API. Охватывает MVC-контроллеры и Minimal APIs. Отдельный MVC-профиль, если выбран, задаёт только контроллерные соглашения.

## Публичный контракт и транспортные границы

- Описывайте ресурсы и операции по реальным сценариям потребителей, а не именам внутренних сервисов и классов БД.
- Выбирайте HTTP-методы осознанно: чтения должны быть безопасными, повторы изменяющих запросов требуют документированных гарантий идемпотентности.
- В авторитетном контракте определяйте источники ввода, обязательные/необязательные поля, ошибки валидации, успешные/ошибочные статусы, аутентификацию, авторизацию, пагинацию и конкурентность.
- Сохраняйте устойчивые имена маршрутов и версионирование для клиентов. Версионирование по URL, заголовку или media type выбирайте лишь как осознанное решение совместимости. Путь `api/v{version:apiVersion}` **не обязателен** автоматически.
- По умолчанию не публикуйте внутренние доменные сущности или модели хранения как API DTO. Изменения сериализатора и домена не должны молча менять публичный контракт.
- Если принят OpenAPI, сверяйте опубликованную спецификацию с настоящим приложением. Ожидания потребителей определяются развёрнутым HTTP-поведением и утверждённым контрактом, а не старыми примерами.

## Границы приложения и отмена

Model binding разбирает транспортный ввод, но не доказывает владение, авторизацию и бизнес-валидность. Endpoints должны передавать выполнение подходящим сервисам/обработчикам приложения, а не прятать бизнес-логику в HTTP-адаптерах. Ни CQRS, ни определённая шина не обязательны.

При необходимости принимайте `CancellationToken` запроса и передавайте в отменяемый I/O. Отмена HTTP-запроса не откатывает автоматически уже зафиксированную операцию и не доказывает отсутствие доставки сообщения.

## Конкурентность и условные HTTP-запросы

- Поддерживайте и документируйте `ETag` и `If-Match` только когда ресурсы имеют определённую семантику версий.
- При ложном условии `If-Match` возвращайте `412 Precondition Failed`. `428 Precondition Required` используйте лишь если API осознанно требует предусловия.
- Конфликт без HTTP-предусловия при необходимости выражается `409 Conflict`. Отличайте конфликт от испорченного ввода.
- Определяйте безопасный повтор после тайм-аутов или неопределённых исходов. Ключи идемпотентности — один из вариантов, а не обязательная реализация.

## Точность запросов, ответов и предусловий HTTP

Различайте **сопоставление маршрута** и валидацию ввода. Ограничение типа вроде `{id:guid}` может привести к `404` для неправильного сегмента даже там, где иной API-контракт ожидает `400`. Используйте route constraints для маршрутизации, а не вместо проверки запроса; испытывайте неверные данные через настоящий HTTP-конвейер.

Если клиенты изменяют ресурсы условно, опишите источник и смысл `ETag` выбранного представления. Для `If-Match` сервер использует **строгое сравнение** текущего представления до записи. Ложное условие обычно даёт `412`; `428` обозначает API, **намеренно требующий** условные запросы, а не стандартный ответ всех обновлений. Не смешивайте HTTP-валидаторы представления с внутренними concurrency tokens, бизнес-версиями и порядковыми номерами интеграций.

ETag не обязан кодировать целочисленный счётчик. Преобразование внутреннего `int Version` в `ETag: "7"` — возможная реализация, не требование HTTP или .NET. Формат обмена, допустимый синтаксис, поддержка wildcard/list и восстановление после несовпадения относятся к принятому контракту. Сервер должен проверять условие на границе, реально предотвращающей устаревшую запись; одного разбора заголовка недостаточно.

Запрос может завершиться до входа в прикладной обработчик, например при маршрутизации, аутентификации, авторизации или привязке. Документируйте эти пути ответа и проверяйте, что метаданные соответствуют фактическому конвейеру. `200` с envelope допустим для выбранного контракта, но **не универсален для всех записей**. `201`, `202` и `204` имеют разный смысл; `204` не содержит JSON body. Если запрос ставит асинхронную работу в очередь с `202`, опишите способ узнать её конечный результат. Бинарные ответы требуют собственного media type и заголовков, а не произвольной JSON-обёртки.

Официальные источники: [маршрутизация ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/routing), [RFC 9110: условные запросы](https://www.rfc-editor.org/rfc/rfc9110#section-13), [HTTP-статусы](https://www.rfc-editor.org/rfc/rfc9110#section-15).

## Статусы и ошибки

Используйте статусы по смыслу: `201` для создания ресурса, `202` для принятой асинхронной работы, `204` для успешного ответа без body, `400` для неверного запроса, `401` для отсутствующей/некорректной аутентификации, `403` для запрета, `404` для отсутствующего или намеренно скрытого ресурса, `5xx` для серверных отказов. Это контекстные примеры, а не полное сопоставление.

Используйте согласованный структурированный формат ошибок; см. [валидацию и ошибки](errors-and-validation.md). Не раскрывайте клиентам stack trace, пароли или сырые исключения инфраструктуры.

## OpenAPI и совместимость

ASP.NET Core имеет встроенную генерацию OpenAPI через `Microsoft.AspNetCore.OpenApi`; другие поддерживаемые инструменты — альтернативы. Объявляйте `ProducesResponseType` и аналоги только для реального поведения. Изменение route constraints, обязательности, enum, типов полей и ошибок анализируйте на совместимость.

При публикации OpenAPI endpoint ограничивайте доступ по окружению и политике. Генерация документа не гарантирует правильности всех сценариев выполнения.

## Проверка

Применяйте HTTP-тесты уровня приложения для маршрутизации, binding, авторизации, ошибок, отмены и совместимости API. Поведение инфраструктуры/провайдера проверяйте отдельно; reverse proxy, CORS и аутентификационные интеграции тестируйте, если этого требует развёртывание.
