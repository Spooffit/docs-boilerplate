# Testcontainers для .NET

**Применимость:** наборы тестов, использующие Testcontainers for .NET с одноразовыми контейнерными зависимостями.

## Имена ресурсов и сеть

- Используйте создаваемые имена контейнеров, сетей и томов вместо фиксированных.
- Позвольте Docker назначать опубликованные порты динамически и получайте фактическое сопоставление.
- Подключайтесь по host и опубликованному порту, сообщённым контейнером; не прописывайте `localhost` жёстко.
- Для взаимодействия контейнеров используйте сетевые псевдонимы и внутренние порты.
- Закрепляйте версии образов; обновляйте осознанно.

## Жизненный цикл и очистка

- Запускайте зависимости до клиентов, ожидайте содержательной готовности, а не произвольный тайм-аут старта.
- Предпочитайте фикстуры с явным владением ресурсами и освобождением.
- Не отключайте Testcontainers Resource Reaper как обычный обходной путь: он очищает оставшиеся после сбоев тестовые ресурсы.
- Доступ к Docker, права на приватный registry и совместимость контейнерного рантайма — явные предусловия CI.
- Не делите изменяемые базы, очереди и схемы между параллельными заданиями без изоляции.

## Логическая изоляция при общих контейнерах

Один одноразовый контейнер PostgreSQL может обслуживать несколько тестов **только если** каждая параллельно записывающая область владеет своей базой или другая изоляция доказуемо предотвращает конфликты. Средства сброса БД подходят для безопасно упорядоченных областей: не сбрасывайте общую изменяемую базу, пока другие тесты работают с ней.

Фикстура RabbitMQ может использовать отдельный virtual host для каждой независимой параллельной области, сохраняя типовые имена exchange/queue внутри неё. Изолируйте привязки и состояние потребителей. Для тестирования конфигурации всего брокера, плагинов, политик, перезапусков узла и восстановления брокера лучше отдельный контейнер.

Создавайте и освобождайте ресурсы в соответствии с **реальным владельцем фикстуры**. Resource Reaper помогает с забытыми контейнерами, но не заменяет правильное освобождение баз, vhost и логических ресурсов. Настраивайте общий бюджет конкурентности CI после измерения совокупных Integration/Functional/E2E нагрузок, а не по фиксированному числу из шаблона.

## Различайте области тестирования

Используйте реальные зависимости при проверке поведения провайдера, миграций, SQL, маршрутизации, сериализации и восстановления после отказа. Не каждому Unit-тесту нужен Testcontainers; не каждый Functional-тест требует всю распределённую систему.

## Проверка

Проверьте закреплённые образы, уникальные имена, ожидание готовности, опубликованные порты, очистку, предусловия CI и отрицательные сценарии.

Официальные источники: [практики](https://dotnet.testcontainers.org/api/best_practices/), [Resource Reaper](https://dotnet.testcontainers.org/api/resource_reaper/).
