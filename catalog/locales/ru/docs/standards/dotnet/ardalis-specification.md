# Соглашения Ardalis.Specification

**Применяется к:** .NET-приложениям, явно выбравшим Ardalis.Specification для композиции намерений запросов.

## Назначение и применимость

Specification описывает выборку, фильтрацию, сортировку, проекцию или пагинацию как переиспользуемый и проверяемый объект запроса. Используйте паттерн, когда связанные запросы выигрывают от обнаруживаемости и композиции. Не требуйте спецификацию вокруг каждого прямого EF Core или Dapper-запроса.

## Семантика и композиция

- У каждой спецификации должна быть понятная цель. Избегайте «универсальных запросов», принимающих произвольный транспортный ввод без бизнес-границ.
- Переиспользуйте действительно общие устойчивые predicates, но не объединяйте разный бизнес-смысл только из-за совпадения CLR-типов.
- Применяйте авторизацию в доверенной логике приложения/доступа к данным. Спецификация по выбору вызывающего не доказывает права.
- Явно различайте выбор сущностей и проецируемых DTO; проверяйте трансляцию провайдером, порядок и пагинацию.
- Для запросов БД подтверждайте серверную трансляцию композиции, избегая неограниченной загрузки строк ради клиентской фильтрации.
- При объединении спецификаций проверяйте API фактически установленной версии. Не пишите примеры по предполагаемым перегрузкам или методам репозитория.

## Повторно используемые predicates и полные спецификации

Библиотека **не предоставляет** общую композицию целых спецификаций через `specA.And(specB)`, `specA.Or(specB)` или `specA.Not()`. Specification может также задавать includes, ordering, projections, tracking и pagination, поэтому считать всю спецификацию одним Boolean predicate некорректно.

- Для атомарных повторно используемых условий предпочитайте узкие extension methods `ISpecificationBuilder<T>`. Пусть каждая `Specification<T>` конкретной операции вызывает подходящие расширения и задаёт собственный формат результата.
- Повторно используемое условие не должно скрыто задавать tracking, сортировку, `Include`, `Skip`, `Take`, проекцию или область разрешений. Держите выбор в итоговой спецификации, не создавайте гигантскую спецификацию с несвязанными переключателями.
- Несколько `Where` сужают результат совместно (AND). Для OR используйте намеренно сгруппированный predicate; два отдельных `Where` не означают OR.
- Передавайте фильтры явно, а не читайте ambient HTTP context или глобальное изменяемое состояние. Создание спецификации описывает запрос и не должно открывать соединения или делать записи.
- Для EF Core используйте evaluator/adapter, поддерживаемый установленной версией, например `WithSpecification`, если он доступен. Не материализуйте данные перед фильтрацией и не вызывайте `Compile()` для DB predicate ради выполнения неподдерживаемой трансляции в памяти.
- Отделяйте постраничную выборку от общего количества совпадений. Для проекций по необходимости выбирайте `Specification<T, TResult>` и обеспечивайте детерминированный порядок, включая равные ключи. Подсчёт и проверка существования должны применять те же **намеренные фильтры**, но не наследовать лимит страницы списка.
- Ограничение доступа и tenant — **обязательные проверки политики** на доверенной границе, а не выбираемые пользователем фильтры.

## Интеграция с БД и тестирование

Ardalis.Specification совместим с EF Core через evaluator/repository инструменты экосистемы. Это выбор интеграции: базовая библиотека сама не выбирает EF Core или PostgreSQL.

Проверяйте семантику predicates небольшими unit-тестами, когда достаточно, и реальной БД, когда важна трансляция SQL или поведение провайдера. Проверяйте пустые страницы, null, устойчивый порядок и производительность больших выборок.
