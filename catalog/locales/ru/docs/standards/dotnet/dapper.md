# Доступ к данным с Dapper

**Применяется к:** .NET-проектам, намеренно выбравшим Dapper. Dapper — лёгкий объектный mapper; он не предоставляет полноценные миграции схемы или отслеживание объектов ORM.

## SQL и безопасный ввод

Параметризуйте пользовательские значения, не конкатенируйте строки напрямую в исполняемый SQL. При динамическом выборе таблицы, столбца или сортировки используйте строгий проверенный allowlist. Применяйте правильные параметры диалекта и явное сопоставление неоднозначных имён столбцов.

## Подключения, время жизни и транзакции

Явно определяйте владельца и срок жизни соединения, границы транзакций, отмену и тайм-ауты команд. Если API и провайдер поддерживают, используйте `CommandDefinition` для передачи токенов отмены.

Запрос внутри ambient или явной транзакции должен использовать правильное соединение и транзакцию. Если многошаговое изменение обещает атомарность, проверяйте откат при отказах.

## Качество запросов и проверка

Оценивайте производительность SQL на характерной нагрузке и задавайте явную пагинацию для больших наборов данных. Проверяйте параметры, отображение строк, null, транзакции и нарушения ограничений на реальном провайдере.

Не требуйте абстракцию repository вокруг каждого вызова Dapper автоматически. Выбирайте границы абстракций по ответственному компоненту и архитектуре проекта.

Источник: [репозиторий Dapper](https://github.com/DapperLib/Dapper).

## Границы запросов и согласованность

- Фильтры, авторизацию, сортировку и пагинацию по возможности выполняйте в параметризованном SQL. Имена колонок и направления сортировки из входных данных должны проходить строгий allowlist: параметры защищают значения, а не SQL-идентификаторы.
- Для offset-пагинации используйте стабильный порядок с уникальным дополнительным ключом. Проверяйте планы выполнения и индексы на характерных объёмах. Если API возвращает общее количество записей, определите контракт его вычисления.
- Явно различайте отсутствие строк, SQL NULL и отсутствие обязательного поля. Для multi-mapping и связей один-ко-многим определите сборку результатов и устранение дубликатов; Dapper не собирает граф связанных объектов автоматически.
- Не используйте одно открытое соединение параллельно без подтверждённого контракта провайдера и владения. Каждая команда явной транзакции должна получать нужное соединение и объект транзакции.

## Надёжность и обработка ошибок

- Передавайте токены отмены и задавайте тайм-ауты команд осознанно. Тайм-аут не доказывает откат записи. Проверяйте rollback и неопределённый результат при обрыве сети.
- Переводите нарушения уникальности, конфликты конкурентных изменений и deadlock на границе доступа к данным без раскрытия SQL, паролей или строк подключения. Повтор записи допустим только при определённой идемпотентности и транзакционной семантике.
- Для миграций используйте отдельный инструмент или явную процедуру развёртывания схемы: Dapper не управляет миграциями.

## Проверки

Запускайте тесты на реальном провайдере: типизированные параметры, null, multi-mapping при использовании, сортировка, пагинация, rollback, конфликты и регрессии планов запросов. Фиксируйте версии драйвера/базы и реально выполненные команды; пример SQL не доказывает production-корректность.
