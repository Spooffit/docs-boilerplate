# Обмен сообщениями через MassTransit и RabbitMQ

**Применяется к:** .NET-приложениям, сознательно выбравшим MassTransit с транспортом RabbitMQ. Ни брокер, ни его топология не обязательны для .NET или CQRS.

## Необязательная композиция EventBus из трёх проектов

Большое .NET-решение может явно принять структуру `Integration/EventBus` с тремя проектами и соответствующей папкой решения:

- `{Solution}.Integration.EventBus.Contracts`: независимые от транспорта сериализованные интеграционные события, контракты команд/запросов/ответов и простые DTO. Без consumers, хранения и топологии RabbitMQ.
- `{Solution}.Integration.EventBus.RabbitMq`: зависит от Contracts и выбранных транспортных пакетов; владеет общими настройками сообщений MassTransit/RabbitMQ и топологией publish/send.
- `{Solution}.Integration.EventBus.Default`: ссылается на Contracts и RabbitMq, предоставляет выбранную проектом регистрацию зависимостей без дублирования сообщений и правил брокера.

Направление зависимостей: Contracts ← RabbitMq ← Default. Приложения-потребители владеют своими receive endpoints. Contracts могут использовать транспортно-нейтральный пакет абстракций, **если это оправдано выбранным API контрактов**, но обязательности нет. DTO контрактов не должны раскрывать изменяемые доменные сущности.

Это **необязательное архитектурное соглашение** при явном выборе, а не универсальная структура папок. Центральный компонент топологии нужен только если полезен проекту; имя `{Context}TopologyRegistrar` также необязательно. Чистому проекту композиции не нужны искусственные сервисные типы. При выборе варианта проверяйте зависимости пакетов, направление ссылок и папки решения.

## Контракты, адаптеры и владение топологией

- Храните DTO сообщений и правила совместимости на контрактной границе без зависимостей от внутренних application/domain типов и транспорта RabbitMQ.
- Оставляйте бизнес-логику в приложении или обработчиках consumers, а не в конфигурации брокера.
- У конфигурации exchange, routing key, очередей и subscriptions должен быть явный владелец. Не дублируйте произвольные строки обменников у publishers и consumers.
- Деление `Integration/EventBus/Contracts`, `RabbitMq`, `Default` может помочь большим модульным решениям, но не требуется MassTransit.
- Очереди и bindings определяются ответственностью приложения-потребителя. Общая очередь означает конкурирующих consumers, а не широковещательную доставку каждому сервису.

## Exchange и устойчивая идентичность сообщения

Топология публикации RabbitMQ обычно использует exchange по типу сообщения с дефолтами и переопределениями MassTransit. Изменение имени сущности обменника поддерживает `SetEntityName`, типы exchange и bindings настраиваются через publish/send и receive topology.

- Проектируйте устойчивые внешние имена exchange и версии сериализованных контрактов независимо от произвольного переименования CLR.
- Выбирайте `fanout`, `direct`, `topic` по реальным правилам маршрутизации. **Не требуйте `fanout` для каждого сообщения.**
- Явные привязки и routing keys должны согласовываться с типом exchange. Для `topic` шаблон binding потребителя и ключ публикации составляют реальный протокол.
- Документируйте durability, auto-delete и отказы production; не меняйте их незаметно при рефакторинге.
- Приложение-потребитель определяет имя очереди endpoint и своего обработчика. Publisher не обязан знать список сервисов-потребителей.

## Явная топология и корреляция

Если сообщение публикуется во внешне потребляемый устойчивый exchange, фиксируйте его идентичность централизованно. Формат `msg.{integration}.{purpose}` — **возможное проектное соглашение**, но не обязательный стандарт MassTransit. Определите политику переименования и сосуществования, чтобы рефакторинг CLR-типа или namespace не переименовал внешний exchange молча. По необходимости используйте совместимый с выбранной версией API `SetEntityName` или согласованный entity-name formatter.

Выбирайте тип exchange (`fanout`, `direct`, `topic`), durability и auto-delete по реальному контракту интеграции. Стандартная publish topology MassTransit может уже иметь нужные настройки; **не навязывайте** всем сообщениям скопированный `fanout` registrar. Для `direct`/`topic` проверяйте routing keys publisher по фактическим bindings; объявить exchange недостаточно для доставки подписчику.

Если корреляция входит в контракт, определите исходное поле, его отображение в заголовок envelope и отличие от ID сообщения и ID доменного агрегата. MassTransit поддерживает `CorrelationId` по соглашению и явный `UseCorrelationId`. Не генерируйте новый несвязанный correlation value в общем registrar, когда он уже есть в сообщении.

Общая publish/message topology допустима, но queue names, receive endpoints, consumers и специфичные retry/redelivery настройки принадлежат приложению-потребителю. Для широковещательной публикации независимым сервисам нужны отдельные очереди: общая очередь означает конкуренцию.

## Надёжность и семантика доставки

- При at-least-once consumer может получать дубликаты. Делайте бизнес-эффекты идемпотентными на выбранном окне обнаружения повторов.
- Retry/redelivery, in-memory outbox, transactional bus outbox и transactional consumer outbox решают **разные** типы отказов. Выбирайте подходящий механизм по реальным требованиям и владельцам данных.
- Для записи БД вместе с публикацией события transactional outbox может согласовывать сохранение и исходящее сообщение; доставка и фиксация у потребителя всё равно отдельные.
- Correlation IDs и message IDs помогают диагностике, но не доказывают exactly-once доставку.
- Применяйте ограниченные повторы, обработку ошибок/dead-letter, мониторинг и восстановление poison messages по потребностям consumer.
- Проверяйте гарантии порядка, только если они требуются контрактом; не предполагайте глобальный порядок в масштабируемой системе.

## Outbox и эволюция контрактов

Когда приложение меняет БД и публикует событие, документируйте риск двойной записи. Transactional outbox — распространённое решение, но **не обязателен каждому взаимодействию**; используйте существующий механизм, если гарантии подходят. Отличайте буфер in-memory outbox, устойчивый bus outbox, consumer outbox/inbox и broker retry. Outbox не отменяет at-least-once и не гарантирует exactly-once бизнес-эффекты.

Имена/типы сериализованных полей, корреляция, устойчивая топология, имя/тип exchange, routing keys и bindings — поверхности версионирования контракта. Совместимость иногда требует параллельных bindings, двойной публикации или последовательного внедрения consumers; semver пакета не гарантирует wire-совместимость. Фиксируйте необходимость версии по фактическим потребителям, не навязывая общую схему каждому приватному сообщению.

## Управление изменениями и тесты

Переименование внешнего ID сообщения, exchange, routing key, binding или сериализованного поля может сломать существующих consumers. Рассматривайте это как изменение интеграционного контракта с планом миграции/версионирования.

Тестируйте сериализацию контрактов отдельно от живой маршрутизации RabbitMQ. Для интеграционных проверок exchange, bindings и receive endpoints используйте одноразовый экземпляр RabbitMQ; дубликаты, повторы и восстановление outbox проверяйте на соответствующих границах.
