# Предметно-ориентированное проектирование (DDD)

**Применяется, когда:** проект сознательно выбирает Domain-Driven Design. DDD не обязателен для .NET, HTTP API или репозитория документации.

## Язык предметной области и границы

Совместно с экспертами предметной области выявляйте термины, поведение, правила и конфликты на языке бизнеса. Сохраняйте терминологию внутри контекстов: одно слово может иметь разные значения в разных ограниченных контекстах.

Определяйте ограниченные контексты по согласованности модели и языка, а не по папкам решения или единицам развёртывания. При взаимодействии контекстов документируйте их отношения и контракты интеграций. DDD не требует микросервисов, CQRS, event sourcing, репозитория для каждого типа или фиксированного числа слоёв.

## Сущности, объекты-значения и агрегаты

Используйте сущности, когда важна непрерывность идентичности, и объекты-значения, когда подходит равенство по смысловому значению. Вводите агрегаты только при обоснованной границе согласованности. Инварианты агрегата должны проверяться на правильной доверенной границе, в том числе при конкурентных изменениях.

Храните доменное поведение у его владельца вместо дублирования одного правила между несвязанными валидаторами и UI. Прикладные сервисы могут координировать операции; инфраструктурные адаптеры работают с выбранными внешними системами. Точные сборки, паттерны хранения и соглашения именования остаются архитектурными решениями.

## Правила и валидация

Отделяйте устойчивые доменные ограничения от проверок транспорта, авторизации и целостности хранения. При допустимых границах зависимостей переиспользуйте одинаковые определения доменных правил, но не приравнивайте случайно совпавшие числовые пределы. Проект может выбрать классы ограничений, методы или объекты-значения; обязательного файлового паттерна нет.

Для принятых доменных значений определяйте значимое равенство, нормализацию, различие отсутствия/null, точность и сравнение только когда это влияет на реальную модель. Не переносите в стандарт DDD общие схемы полей, редактирование версионируемых сущностей, публикацию, согласование или жизненные циклы исторических снимков.

## События и интеграции (при необходимости)

Доменные события выражают факты внутри модели; интеграционные события — внешние контракты. Не каждый агрегат должен порождать события. При пересечении границы системы описывайте гарантии доставки, повторы и побочные эффекты, а не предполагайте единую атомарную транзакцию для сохранения и отправки.

## Проверка

Используйте примеры из **согласованной предметной области текущего проекта**, чтобы проверить границы агрегатов, инварианты и согласованность языка. Для наблюдаемых правил применяйте доменные тесты, для реальных гарантий хранения и сообщений — интеграционные. Не вводите демонстрационные доменные сущности как обязательные требования универсального шаблона.
