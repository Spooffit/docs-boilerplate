# Предметно-ориентированное проектирование (DDD)

**Применяется при осознанном выборе DDD.** .NET, HTTP API и документация не требуют DDD.

## Язык и границы предметной области

Уточняйте понятия, поведение и конфликты с экспертами предметной области. В разных bounded context один термин может иметь разные значения. Стройте границы на основании согласованной модели, а не по папкам и сервисам. DDD не требует микросервисов, CQRS, event sourcing и фиксированного числа слоёв.

## Сущности, объекты-значения и агрегаты

Сущность уместна при устойчивой идентичности; value object — при сравнении по значению. Агрегат вводите ради реальной границы согласованности и инвариантов. Не создавайте репозиторий, событие или класс для каждого типа без причины.

## Правила и проверка

Инварианты защищайте на доверенной границе изменения состояния. Отличайте валидацию входных данных от правил модели. Проверка UI не заменяет проверку на сервере.

## События и интеграции

Доменные события, внешние сообщения и команды различаются. Документируйте семантику, доставку и восстановление только при реальном использовании.

## Проверка

Проверяйте язык на бизнес-примерах, инварианты — тестами, а интеграцию — через реальный контракт.
