# Необязательный HTTP-контракт конкурентности на основе строгого ETag и If-Match

**Применяется, когда:** выбран профиль `http-etag-concurrency` для HTTP-ресурсов с явно принятым контрактом предотвращения потерянных обновлений через **strong ETag / If-Match**. Базовый [стандарт HTTP-контрактов клиента](client-contracts.md) не требует этого механизма. Пути и значения тегов ниже — намеренно универсальные примеры, а не маршруты проекта или доменные требования.

## Контракт обмена и строгое сравнение

1. Origin server возвращает `ETag` для выбранного представления ресурса с учётом согласованных вариантов представления. Сохраняйте точное непрозрачное значение в кавычках. Не создавайте ETag на клиенте из редактируемого поля и не считайте слабый `W/"..."` строгим.
2. Если обновление требует optimistic concurrency, клиент отправляет `If-Match` с последним полученным строгим валидатором представления. Сервер сравнивает его **строго** с текущим представлением **до применения** изменения, внутри защищённой от гонок транзакции либо эквивалентного условного обновления.
3. При успехе возвращайте соответствующий статус и новый валидатор, если он доступен для итогового представления. Для устаревшего валидатора обычно возвращается `412 Precondition Failed` **без изменения данных**. `If-Match: *` проверяет наличие текущего представления, а не конкретную ревизию.
4. Если API явно требует предусловие, а оно отсутствует, запрос может быть отклонён с `428 Precondition Required` (RFC 6585). `409 Conflict` относится к независимому конфликту приложения и не заменяет неуспешный `If-Match`. Некорректные заголовки обрабатывайте по выбранному контракту, не игнорируйте молча.
5. Проверка предусловий следует HTTP-семантике, в том числе зависит от того, завершился бы метод успешно без них. Проверяйте авторизацию и существование ресурса по принятому API; условные заголовки не должны раскрывать защищённые ресурсы. `If-None-Match` имеет другую семантику и не является псевдонимом `If-Match`.

## Справочные сценарии запросов и ответов

Каждая пара — **иллюстративный** HTTP/1.1-обмен для условного ресурса `/resources/42`. Последовательность начинается с `"rev-7"`; одно успешное обновление изменяет тег на `"rev-8"`. Контрактные тесты проверяют значения тегов, статусы и переходы ETag; они **не запускают реальный HTTP-сервер**. Тела и заголовки оставлены неизменными, чтобы технические проверки на любом языке использовали одинаковые примеры.

```http scenario=read
GET /resources/42 HTTP/1.1
Host: api.example.test

HTTP/1.1 200 OK
Content-Type: application/json
ETag: "rev-7"

{"value":"before"}
```

```http scenario=success
PUT /resources/42 HTTP/1.1
Host: api.example.test
Content-Type: application/json
If-Match: "rev-7"

{"value":"after"}

HTTP/1.1 204 No Content
ETag: "rev-8"
```

```http scenario=stale
PUT /resources/42 HTTP/1.1
Host: api.example.test
If-Match: "rev-7"
Content-Type: application/json

{"value":"outdated"}

HTTP/1.1 412 Precondition Failed
```

```http scenario=weak
PUT /resources/42 HTTP/1.1
Host: api.example.test
If-Match: W/"rev-8"
Content-Type: application/json

{"value":"cannot-match-strongly"}

HTTP/1.1 412 Precondition Failed
```

```http scenario=missing
PUT /resources/42 HTTP/1.1
Host: api.example.test
Content-Type: application/json

{"value":"without-guard"}

HTTP/1.1 428 Precondition Required
```

```http scenario=conflict
PUT /resources/42 HTTP/1.1
Host: api.example.test
If-Match: "rev-8"
Content-Type: application/json

{"value":"violates-an-independent-constraint"}

HTTP/1.1 409 Conflict
```

## Реализация и проверка

- **Атомарность:** две конкурентные записи с одним актуальным ETag не должны обе перезаписать друг друга. Применяйте compare-and-write внутри подходящей транзакции, условия версии или эквивалентной гарантии хранилища. Проверка ETag заранее в handler недостаточна.
- **Регрессия:** чтение валидатора, успешная условная запись с новым тегом, отклонение устаревшего значения без изменения данных, отклонение слабого тега, отсутствующее обязательное предусловие, авторизованный/отсутствующий ресурс и независимый `409` при совпавшем ETag.
- **Повторы:** тайм-аут после условной записи означает неопределённый исход. Повтор со старым ETag может получить `412`, поскольку первая запись была зафиксирована. Перечитайте и согласуйте результат либо используйте утверждённый механизм идемпотентности; не обновляйте тихо тег ради повторной перезаписи.
- **Границы доказательства:** `tests/optional_profile_contracts.py` проверяет примерные обмены по детерминированной модели. Каждый проект должен дополнительно тестировать собственные API, транзакции хранилища и безопасность.

Источники: [RFC 9110, §13.1.1 If-Match](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.1), [RFC 9110, §8.8.3.2 строгое сравнение](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.2), [RFC 6585, §3 (428)](https://www.rfc-editor.org/rfc/rfc6585#section-3).
