# Проверка HTTP API-контрактов и совместимости

**Применяется, когда:** у HTTP API есть опубликованные потребители или требования к совместимости.

## Авторитетный контракт

Определите утверждённый публичный контракт, его версию или ссылку и развёрнутое поведение, которое тестируется. OpenAPI или иное машиночитаемое описание может быть основным источником, если проект его принял. Пример контроллера или исторический документ не доказывает работу развёрнутой системы.

Проверьте метод, URL, типы запросов/ответов, обязательность, nullability, тело ошибки, коды статуса, заголовки, область безопасности и сериализацию выбранного endpoint. Явно отмечайте непроверенное; не создавайте endpoints и DTO ради заполнения пробелов документации.

## Проверка совместимости

Для изменений, влияющих на потребителей, анализируйте ограничения маршрутов, значения query по умолчанию, новые обязательные поля, неизвестные значения enum, отсутствие против `null`, числовую точность, даты и смещения, коллекции, content type, пагинацию, аутентификацию, условные запросы и отображение ошибок. Включайте только реально присутствующие в публичном контракте аспекты.

Совместимое изменение на уровне языка может сломать потребителя по сети. Разделяйте имена свойств, отображаемые подписи и значения полей, если схема определяет их. Не навязывайте особую модель идентичности доменных полей или исторических версий.

Проверяйте фактическую среду клиента, особенно заголовки ответа, ошибки, типы/nullability и сериализатор. Выбор моделей UI описывается отдельно выбранными соглашениями состояния форм, а не самим публичным API-контрактом.

## Доказательства и внедрение

Для изменённой операции записывайте согласованный целевой контракт, наблюдаемую реализацию, совместимость клиента (если известна), доказательства реально выполненных тестов и расхождения. Историческая ревизия не доказывает развёрнутый маршрут. Предложенная матрица без успешных запусков — план, а не проверка.

Оценивайте совместимость старых/новых потребителей и порядок развёртывания только для реально сосуществующих версий. Документируйте применимые сроки устаревания и ожидания отката; не придумывайте схему версионирования API.

## Проверка

Тестируйте реальный транспорт и выбранный клиент/рантайм. Проверяйте обязательные и пропущенные значения, неавторизованный доступ, формат ошибок, соответствие статусов/заголовков и обратную совместимость согласно подтверждённым обязательствам. Одна успешная сборка не доказывает совместимость обмена.

Источники: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110), [OpenAPI Specification](https://spec.openapis.org/oas/latest.html).
