# HTTP-контракты клиентов и надёжные запросы

**Применяется к потребителям HTTP API.** Не требует конкретного фреймворка, стратегии версий API или модели UI.

## Авторитетный контракт

Методы, пути, заголовки, поля, nullable, ошибки и авторизацию берите из принятого публичного контракта, а не внутренних сущностей или старого примера контроллера. Проверяйте сериализацию и необходимые метаданные ответа. Модель отображения не должна изменять сетевой формат.

## Транспорт, отмена и ресурсы

Для потоковых ответов определяйте момент доступности заголовков, владение потоком, освобождение ресурсов и ограниченную буферизацию. Отмена на стороне клиента не доказывает отмену серверного эффекта.

## Условные запросы

Применяйте ETag, If-Match, If-None-Match и диапазоны только по поддерживаемому контракту. Не вычисляйте серверные валидаторы из редактируемых полей.

## Повторы и неизвестный результат

Таймаут или потерянное подтверждение не означают, что запись не выполнена. Автоматический retry изменяющего состояния запроса допускается лишь при подходящем контракте идемпотентности или запроса результата. Определяйте отмену, backoff и лимиты по реальным требованиям.

## Проверка

Тестируйте метод, тело, заголовки, ошибки, отмену, неопределённый результат и совместимость с настоящим сервером. Мокированный HTTP доказывает поведение клиента, а не сервера.
