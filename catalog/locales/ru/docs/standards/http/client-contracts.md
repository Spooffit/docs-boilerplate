# HTTP-контракты клиентов и надёжная обработка запросов

**Применяется, когда:** проект потребляет HTTP API. Не требует фреймворка, стратегии версионирования API или определённой архитектуры состояния UI.

## Исходный контракт и клиентское представление

Используйте принятый публичный HTTP-контракт для определения методов, маршрутов, заголовков, полей запросов/ответов, nullable, ошибок и безопасности. Не выводите внешний формат из внутренней сущности или старого примера контроллера.

Проверяйте клиентские представления запросов и ответов по авторитетному публичному контракту API. Сохраняйте метаданные транспорта, включая заголовки ответа, когда это требует контракт. Клиентские модели отображения допустимы, но не должны переопределять формат обмена.

## Транспорт, отмена и владение ресурсами

Для потоковых ответов документируйте момент доступности заголовков, владение body, освобождение и ограниченную буферизацию. Явно определяйте семантику отмены: прекращение локального ожидания не обязательно останавливает зафиксированную удалённую операцию. Не добавляйте лишние уровни клиентского состояния или кэша без конкретной потребности.

Не раскрывайте секреты в URL, диагностике и ошибках. Ошибки аутентификации, запрет авторизации, отсутствующие и скрытые ресурсы обрабатывайте согласно реальному контракту сервера; не превращайте отказы безопасности в пустые успешные ответы.

## Условные запросы (если поддерживаются)

Если сервер использует валидаторы ресурса, сохраняйте точный `ETag` соответствующего представления. Для `If-Match` HTTP задаёт строгое сравнение. Не придумывайте токен из поля UI и не обновляйте молча устаревший валидатор с перезаписью чужих изменений.

Различайте `412 Precondition Failed`, `428 Precondition Required` и `409 Conflict` по контракту: эти статусы не взаимозаменяемы. После успеха используйте возвращённый новый валидатор или при необходимости перечитайте ресурс.

## Тайм-ауты, повторы и неопределённые исходы

HTTP-тайм-аут не доказывает откат изменения. Отличайте точно неотправленные запросы, подтверждённый успех, подтверждённый отказ и неопределённый исход.

Безопасные/идемпотентные запросы можно повторять в пределах ограниченной транспортной политики. Для неидемпотентных операций повторы допустимы только при принятом контракте идемпотентности или запроса исхода с сохранением согласованного ID операции и значимых параметров. Одинаковые тела запроса не обязательно выражают одинаковое намерение пользователя.

Не считайте `202 Accepted` завершённым результатом, если контракт этого не обещает; иначе следуйте реальному механизму статуса операции. Разбирайте стандартизированные форматы ошибок, например Problem Details, только когда API действительно их публикует.

## Проверка

Проверяйте сериализацию, отсутствующие и null-поля, границы авторизации, ожидаемые статусы, обязательные заголовки, отмену, повторы и неопределённые исходы на реальном сервисе или точной контрактной среде. Успешная сборка не доказывает совместимость выполнения.

Источники: [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110), [Problem Details RFC 9457](https://www.rfc-editor.org/rfc/rfc9457).
