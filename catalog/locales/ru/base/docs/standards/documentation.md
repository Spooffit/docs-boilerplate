# Правила оформления документации

**Применяется к:** каждому репозиторию документации, созданному генератором.

## Авторитетные источники и навигация

- **Markdown-файлы**, а не сайт для просмотра, являются авторитетной документацией проекта.
- Используйте корневой `llms.txt` как краткую точку входа, а `AGENTS.md` — как инструкции. Ни один из них не заменяет исходные документы и явные решения проекта. Полная карта проектных документов, включая созданные после инициализации, находится в `docs/catalog.md`. `llms.txt` специально остаётся коротким и должен ссылаться на каталог, а не повторять каждый новый файл. Изначальные индексы перечисляют установленные документы, а не ожидающие или невыбранные технологии. Навигация не означает согласования требований.
- Каждый каталог в `docs/`, содержащий Markdown, должен иметь `index.md`, описывающий назначение каталога и ссылающийся на его содержимое. Ссылки должны быть относительными к текущему документу. При добавлении страницы включите ссылку в ближайший `index.md` и `docs/catalog.md`. Для нового вложенного каталога добавьте ссылку на его `index.md` также в родительский индекс. После перемещения или переименования обновите соответствующие индексы, каталог и входящие ссылки. Генератор создаёт исходные индексы, но **не перезаписывает пользовательские изменения** ради исправления навигации.
- Документы называют в нижнем регистре с **kebab-case**, например `api-versioning.md`; обзоры каталогов — `index.md`. Установленные инструментами имена `README.md`, `AGENTS.md`, `SKILL.md` и `CONTRIBUTING.md` являются разрешёнными исключениями. Не переименовывайте их.
- **Каждая Markdown-страница в `docs/` по умолчанию имеет устойчивый `id` в YAML frontmatter.** Генератор назначает детерминированный уникальный идентификатор при создании. Сохраняйте его при переименовании и перемещении; для новой страницы выбирайте уникальный ID. Это технический ключ, а не номер требования, хронологическая последовательность или подтверждение согласования. Имена файлов выбирайте независимо. Не придумывайте согласования и статусы утверждения. См. [устойчивые идентификаторы](document-identifiers.md).

## Frontmatter

Каждая обычная страница Markdown в `docs/` начинается одним блоком YAML frontmatter. **Корневой `README.md` является исключением**: он должен начинаться с заголовка `#`, поскольку GitHub отображает YAML frontmatter в начале README как нежелательную таблицу метаданных:

```yaml
---
id: doc-0123456789abcdef
title: "Пример заголовка"
description: "Краткое описание на основе фактов"
kind: standard
status: active
---
```

Поля обязательны и имеют следующий смысл:

| Поле | Значение |
| --- | --- |
| `id` | Уникальный устойчивый идентификатор, сохраняемый при переносе и переименовании |
| `title` | Понятное человеку имя документа, согласованное с H1 |
| `description` | Краткое фактическое описание для поиска и ИИ-агентов |
| `kind` | `index`, `standard`, `template`, `project`, `guide`, `reference`, `adr` или `audit` |
| `status` | `active`, `draft`, `template` или `superseded` |

CLI проверяет уникальность ID; приведённый идентификатор — пример. Не добавляйте вымышленных владельцев, дат пересмотра, статусов принятия и неподтверждённых ограничений версий технологий. Если владельцы или даты действительно необходимы, сначала утвердите и задокументируйте изменение схемы, а затем указывайте только реальные значения. Метаданные должны быть краткими.

`SKILL.md` — **особый случай**: сохраняйте поля `name` и `description` во frontmatter спецификации навыка агента, не заменяя их `title`/`kind`/`status`. Свежесозданные обзоры проекта и архитектуры намеренно имеют `draft` до проверки. Успешная валидация генератора подтверждает структуру, а не факты или согласование владельцем.

## Правила ссылок

- Пишите относительные пути с расширением `.md` к существующим документам.
- Для ссылки на раздел используйте соответствующий Markdown-фрагмент, например `[область](feature.md#scope)` или `[проверки](#checks)`. Предпочитайте короткие и устойчивые заголовки; повторяющиеся получают числовые суффиксы вроде `#setup-1`. При необходимости кодируйте не-ASCII символы в URL-фрагментах.
- CLI проверяет обычные ссылки, локальные фрагменты и распространённые варианты заголовков ATX/Setext, игнорируя примеры внутри fenced code block. Он **не реализует** все правила CommonMark и Docsify для якорей. Проверяйте результат отображения, если используете специфические заголовки.
- После переноса страницы обновляйте входящие ссылки.
- Ссылайтесь на основной стандарт, контракт, ADR или функцию, вместо копирования.
- Технические стандарты описывают проверяемые правила и должны явно определять применимость. Необязательные библиотеки требуют выбранных технологических профилей.
- Шаблон — подсказка, а не подтверждение утверждённой или готовой реализации. Список установленных технических профилей также не подтверждает бизнес-требований.
- Для **принятых решений** используйте основной ADR/решение и требования; для внешнего формата обмена — принятую схему и фактический контракт; для текущей реализации — проверенный код и реальные тесты. При противоречиях выясняйте источник конфликта и ответственного, а не автоматически предпочитайте кажущийся более новым документ.
- Читайте лишь материалы, относящиеся к текущей задаче. Каталог и руководство по шаблонам служат навигацией, а не причиной расширять каждую категорию документов.

## Примеры кода и доказательства проверки

- Считайте примеры кода **иллюстративными**, если точный фрагмент или его полный эквивалент не был скомпилирован, запущен или проверен контрактными тестами при явно указанном совместимом наборе инструментов. Правдоподобный синтаксис не доказывает работоспособность.
- Когда пример заведомо неполон (псевдокод, тип-заглушка, опущенные импорты, окружение приложения или проверки), **помечайте его как иллюстративный или частичный** рядом с примером. Не представляйте `...` или комментарии вместо исполняемого поведения как проверенный код.
- Заявление об **исполняемом или проверенном** примере требует конкретной команды сборки/теста, инструмента, версий зависимостей при необходимости и доступного доказательства успешного запуска. Ссылайтесь на основной источник тестовых фикстур, вместо дублирования расходящегося примера.
- **Не требуйте** отдельного приложения, пакета или задания CI для каждого небольшого фрагмента. Предпочитайте реальные целевые тесты для примеров, существенно влияющих на интеграции, совместимость, безопасность или публичное поведение. Если проверка не запускалась, пишите *не проверено*, а не утверждайте успешность.
- Одна сборка не доказывает интеграцию, поведение в рантайме, авторизацию, надёжность или совместимость API. Проверяйте утверждение на подходящей границе.

## Просмотр и локальный запуск

Docsify — необязательный интерфейс для чтения в браузере, а не обязательный инструмент сборки. Его `index.html` намеренно отделён от `docs/index.md`. Для локального просмотра обычно нужен HTTP-сервер; открытие через `file://` может не работать.

## Проверки

Если доступны исходники генератора и .NET 10 SDK, выполните **из каталога генератора** `dotnet run --project src/DocsBoilerplate.Cli -- validate --output <repository-root>`. Сгенерированный репозиторий не содержит CLI и не устанавливает его. Без генератора проверьте ссылки, навигацию, метаданные и доказательства вручную, указав, какие автоматические проверки были недоступны.

Валидатор проверяет метаданные, имена файлов, обычные относительные Markdown-ссылки **включая распространённые якоря разделов**, декларации сгенерированных файлов, наличие индексов, доступность всех документов из `docs/catalog.md`, доступность новых пользовательских страниц через непосредственные индексы и ссылки/фрагменты `llms.txt`. Ссылки по меткам, динамические ссылки, сложный Markdown/HTML и произвольные выражения YAML **не обрабатываются полностью**. Проверяйте критичную навигацию между страницами в настроенном браузерном представлении Docsify; успешная проверка исходников не гарантирует совпадения якорей во всех рендерерах.

См. предложение сообщества [llms.txt](https://llmstxt.org/) и [Docsify](https://docsify.js.org/), выполняющие разные роли.
