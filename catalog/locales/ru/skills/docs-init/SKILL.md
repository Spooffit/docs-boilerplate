# Инициализация документации проекта

Навык может быть установлен в **уже инициализированном репозитории**. В таком случае не вызывайте `init` повторно, не предполагайте локальную доступность генератора и не пересоздавайте установленные файлы. Начните с изучения проекта на основе фактов и поддерживайте существующую документацию. Шаги генератора далее относятся только к созданию **нового** каталога из отдельной копии исходников.

1. Подтвердите каталог назначения, имя и фактическое описание. Изучите реальные требования, решения, код, схемы и доступные результаты тестирования/развёртывания. Не придумывайте сведения ради заполнения шаблона.
2. Уточняйте недостающий существенный выбор только при необходимости; неизвестную технологию, архитектуру или поведение отмечайте **Ещё не проверено**.
3. Если установлен инструмент `docs-boilerplate`, выполните `docs-boilerplate list`; иначе, при наличии **копии исходников генератора** и .NET 10 SDK, вызовите из неё `dotnet run --project src/DocsBoilerplate.Cli -- list`. Выбирайте только доступные и применимые технические профили; документационные модули и постоянные навыки агентов включаются по умолчанию. Сгенерированный репозиторий не содержит CLI и не устанавливает его автоматически; выбор профиля не доказывает используемую продуктом технологию.
4. **Только для нового каталога**, из исходников генератора сначала просмотрите `dotnet run --project src/DocsBoilerplate.Cli -- init ... --dry-run`, не допускайте конфликтов и перезаписей. Укажите `--language en|ru`, если язык задан заранее; иначе выберите его в мастере после пути назначения. Выполните согласованный `init`, который автоматически запускает проверку. Docsify добавляет один `index.html` в корне, а `--site none` отключает просмотрщик. Если исходники или SDK недоступны, сообщите об ограничении, не придумывайте команду внутри сгенерированного проекта.
5. Прочитайте сгенерированные `llms.txt`, `AGENTS.md`, `docs/index.md`, `docs/catalog.md` и `docs.config.json`. Убедитесь, что файлы и зависимости соответствуют подтверждённому выбору.
6. **Первичный сбор сведений, включая существующие сгенерированные проекты:** заполните `docs/project/overview.md` и `docs/architecture/overview.md` на основе доказательств. Разделяйте принятую спецификацию и наблюдаемую реализацию; поле `active` во frontmatter или выбранный профиль не доказывают истинность бизнес-утверждений. Отличайте наблюдаемое, принятые цели и открытые решения. Сохраняйте обе страницы в `draft` до проверки; неизвестные факты не считайте предположительно истинными.
7. Создавайте только действительно необходимые документы функций, технических функций, модулей, вопросов, этапов и ADR. Выбирайте минимальный шаблон из `docs/templates/index.md`. Не заполняйте пустые семейства документов заранее.
8. После правок повторно запустите `validate` из исходников генератора, если они доступны; проверьте навигацию, выбранную область и владение файлами. Корректный документ не обязательно является согласованным проектом. Не редактируйте `docs.config.json` вручную.
9. Отчитайтесь об установленных файлах и профилях, действительно проверенных источниках, оставшихся черновиках/открытых вопросах и фактически выполненных тестах.

Для последующих изменений используйте механизм обновления генератора с предварительным просмотром; не дублируйте его правила владения файлами и хеширования в навыке.
