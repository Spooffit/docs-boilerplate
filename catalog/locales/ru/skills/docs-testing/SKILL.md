# Проверка стратегии тестирования

1. Прочитайте `llms.txt`, `docs.config.json`, проектную стратегию тестирования при наличии и применимые технические стандарты.
2. Определите реальную тестируемую систему (SUT) для каждого набора: изолированное правило, взаимодействие с инфраструктурой, публичное поведение приложения, UI-компонент, контракт интеграции или работающий пользовательский сценарий.
3. По реальному коду и заданиям CI подтвердите проверяемые результаты, сценарии отказов, жизненный цикл фикстур, изоляцию, повторы/тайм-ауты и доказательства выполнения.
4. Считайте TUnit, Testcontainers, bUnit, Aspire Testing и конкретные платформы запуска независимыми вариантами выбора. Не заявляйте о совместимости без проверки нужного набора инструментов.
5. Обновляйте `docs/testing/strategy.md` **только если документ существует и уместен**. Модуль тестирования как заготовка устанавливается по умолчанию, но не означает существования тестов или обязанности создать новый документ. Для обоснованной новой страницы используйте YAML frontmatter, имя kebab-case и ссылки из ближайшего `index.md` и `docs/catalog.md`.
6. Отличайте доказательства успешных тестов от предложенных проверок; процент покрытия сам по себе не определяет качество поведения.
7. Для проверки документации запускайте `dotnet run --project src/DocsBoilerplate.Cli -- validate --output <repository-root>` только из **доступной копии исходников генератора** с .NET 10 SDK, иначе проверяйте вручную и сообщайте об ограничении. Команды тестирования проекта запускайте лишь когда они существуют и соответствуют выбранной технологии. Отчитывайтесь о наблюдаемых доказательствах, а не вымышленных успешных проверках.
