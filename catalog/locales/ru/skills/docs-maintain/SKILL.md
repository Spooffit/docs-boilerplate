# Сопровождение документации

1. Начните с `llms.txt` и `docs/index.md`, затем прочитайте затрагиваемый основной стандарт, функцию, ADR или спецификацию проекта.
2. Определите тип изменения: подтверждённое требование, наблюдаемая реализация, принятое решение или предложение. Не превращайте предложение в утверждённое решение.
3. Вносите минимальные правки в авторитетный документ. Добавляйте ссылки в других местах, не дублируйте правила и внешние контракты.
4. Для нового документа в `docs/` используйте корректный YAML frontmatter и содержательное имя в kebab-case. Добавьте его в `index.md` **непосредственного каталога** и `docs/catalog.md` относительными ссылками. Новому подкаталогу нужен собственный `index.md` **и ссылка на него в родительском `index.md`**. Каталог содержит полную карту документов; `llms.txt` — **отобранная точка входа**, а не зеркальная копия списка файлов. Добавляйте туда ссылку только если новая страница действительно важна для начала навигации.
5. При переименовании или переносе найдите все входящие Markdown-ссылки, обновите их (и фрагменты при изменении заголовков), оба затронутых индекса и `docs/catalog.md`. Удалите устаревшие записи. Не подменяйте исторический документ другой страницей лишь ради разрешения ссылки.
6. Если доступны исходники генератора и .NET 10 SDK, выполните из исходников `dotnet run --project src/DocsBoilerplate.Cli -- validate --output <repository-root>`. Проверяются отсутствующие цели и фрагменты заголовков, полнота `docs/catalog.md`, охват новых страниц непосредственными и родительскими индексами. Инструмент **не исправляет** навигацию автоматически, не разбирает все диалекты Markdown и не подтверждает достоверность текста. Проверяйте Git diff и важные переходы Docsify.
7. **Только при наличии исходников генератора и SDK** выполните `dotnet run --project src/DocsBoilerplate.Cli -- update --output <repository-root>` из его каталога для просмотра изменений исходного шаблона; добавляйте `--apply` только после проверки плана. При незавершённом обновлении изучите рабочие файлы и выполните `dotnet run --project src/DocsBoilerplate.Cli -- recover --output <repository-root>` **из исходников генератора** перед новой операцией. Если они недоступны, сохраните журнал и не утверждайте, что восстановление проведено. Никогда не удаляйте временный журнал восстановления ради обхода конфликта. Исходные каталог и индексы принадлежат генератору по хешам; их ручное изменение допустимо, но конкурентное изменение исходного шаблона требует ручного согласования. Не обходите конфликты и не перезаписывайте пользовательскую навигацию.
8. Перечислите изменённые файлы, исправленные ссылки/навигацию, фактически запущенные тесты и оставшиеся неизвестные.

Навыки описывают процесс работы; технические стандарты находятся в выбранных файлах `docs/standards/`.
